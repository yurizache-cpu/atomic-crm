# ADR 0019 — The Company OS operator surface: an in-app module, a function-only RPC schema owned by a least-privilege role, explicit membership, and two narrow browser acts

**Status:** Accepted for implementation (owner decisions 2026-09-22: the owner's review of [PHASE_2C_BRIEF.md](../PHASE_2C_BRIEF.md), then the owner's final confirmation of OD-8a, the membership identity, the residual-trust decisions and the four invariant amendments, then the owner's pre-push review of the exact texts; see "Owner confirmation record" below). **Architecture integrated 2026-09-22:** this record was merged into `feature/clinical-phase-1` by PR #6, normal merge commit `fe7976c5`, reviewed head `95bf2faa`. **Not implemented:** no code, SQL, migration or test exists for it. Implementation waits for planning spikes S0.1 to S0.6 (brief §19, §24) · **Date:** 2026-09-22
**Implemented by:** nothing yet.
**Amends:** [ADR 0004](0004-principal-model.md) (addendum 2026-09-22: the human principal keyed to the auth user id, and tenant-generic membership) and [ADR 0010](0010-cost-control-and-kill-switch.md) (addendum 2026-09-22: the browser may trip, never clear, with bounded contention). **Supersedes for the operator surface:** the browser → `ops-web` → worker HTTP topology in `docs/ARCHITECTURE.md` D1, ADR 0005's line 25 (ops screens using ra-core against a worker API), and the ROADMAP's Phase 7 "Phase-1 UI" scope (`apps/ops-web` on admin guessers).

## Context

Every operator act today runs as `postgres` through `ADMIN_DATABASE_URL` in a CLI. No browser, edge function or human role reaches `ops`; `ops` is not exposed through PostgREST; `anon` and `authenticated` hold no privilege on it, no application role holds a privilege on a Company OS table, and `service_role`, `ops_worker` and `ops_gateway` hold only their pinned grants (SI-15, SI-21, A4). There is no human identity in `ops` (ADR 0004 deferred it), no link from a CRM user to an `ops` tenant, no tenant-scoped read model for events, tasks or agents, and no UI kill switch (the UI half of ADR 0010 2(c) is "Not built"). Every Supabase Auth user is also a CRM user of the tenant that owns the local CRM, and the CRM's `users` edge function lets a CRM administrator change another user's auth email, so today the Auth directory, the CRM and any login-based identity are coupled.

Phase 2C gives the owner a real UI to observe and narrowly steer the Company OS, over real durable state only, while BASELINE Q8 stays open and the production WhatsApp real-data gate stays closed (ADR 0018). The owner reviewed the brief on 2026-09-22, accepted its direction with amendments, and gave the final confirmation and the pre-push review of the exact texts the same day; this record carries those decisions.

## Decision

### 1. Frontend: an in-app, ra-core-free module (OD-1)

The operator surface is a Company OS module at `src/company-os/`, selected by a small top-level switch in `src/App.tsx` on the hash prefix `#/company-os`. It is built on the unmodified `src/components/ui/*`, with its own in-memory query cache and its own router. `<CRM/>` and every file under `src/components/atomic-crm`, `admin` and `ui` stay unchanged, and ESLint bans ra-core, `@supabase/*`, `engine/**` and CRM imports inside the module (the session port is constructed in `src/App.tsx` and injected). No workspace, no `apps/ops-web`. A second Vite entry on the same origin is a fallback only if spike S0.1 proves the in-app boundary impractical; screen code would not change.

### 2. API: a function-only PostgREST RPC schema (OD-2)

The browser calls a dedicated schema, `company_os_api`, exposed on the existing Data API origin. It holds functions only, never a table, view, sequence or type. It is not CRUD, not arbitrary SQL, not table exposure and not a generic `ops` proxy: every RPC is designed and pinned individually, returns one `jsonb` envelope, and takes no tenant, company, actor, reviewer, source or causation argument, no table, function, schema or SQL argument, and no generic "operation" argument. At most 17 functions: 16 for the core screens and 1 for the optional Communications status view. `ops` stays unexposed. No new process, port, origin, credential, CORS or TLS decision is introduced. A generic engine HTTP CRUD service, arbitrary Edge Function SQL and any browser-held database credential are rejected.

### 3. Privilege: a dedicated least-privilege role and a pinned capability graph (OD-8; OD-8a)

Function ownership is not the security boundary. The boundary is the exact callable capability graph. **Function owner** (whose privileges a body runs with) is kept distinct from **effective authority** (what a browser caller can cause).

```
authenticated
  ↓ EXECUTE
company_os_api RPC (SECURITY DEFINER, owned by ops_operator_api)
  ↓
identity and membership gate (ops.gate_<op>, SECURITY DEFINER, one per operation)
  ↓
one approved internal projection or act
  ↓
ops
```

- `ops_operator_api` is a new role: **NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOBYPASSRLS, NOINHERIT**; no login role, no password. It owns exactly the catalogued `company_os_api` functions. It holds USAGE on `ops` and EXECUTE on exactly the gate set; outside `ops`, `pg_catalog` and `information_schema` it can execute only a pinned, measured list (its own functions and what PUBLIC already executes there, the PUBLIC CRM helpers included, listed as existing debt, not approved). It holds **no** table, view, sequence or column privilege outside the catalogue reads PUBLIC gives every role (`pg_catalog`, `information_schema`), no CREATE on any schema or on the database (in particular none on `company_os_api`, `ops` or `public`) and no generic write authority. It has no members: not the migration identity, `authenticated`, `anon`, `authenticator`, `service_role`, `ops_worker` or `ops_gateway`, and no login role's membership closure contains it, so neither the browser (through PostgREST, whatever role a JWT claims) nor any login that is neither a superuser nor a CREATEROLE role can `SET ROLE` into it. A superuser or a CREATEROLE role (such as `postgres`) could first grant itself membership; such a credential is the database-owner trust root, and S0.4 measures and pins which roles hold it.
- `authenticated` holds USAGE on `company_os_api` and EXECUTE on its functions, and nothing on `ops`.
- Each exposed body is exactly one call to its gate. Each gate first resolves the caller (Decision 4), then calls exactly one pinned internal projection or existing service with the resolved tenant and actor, sets `no-store` on the successful response, and raises only fixed, data-free errors. No wrapper can choose a table, function, schema, SQL text, tenant, company, actor, reviewer or an action outside its contract.
- **Why the role executes gates rather than projections.** The services and evaluators run on FORCE-RLS tables with lease-only policies and raise under active row security; a non-superuser `postgres` cannot create a BYPASSRLS role, and table grants would break SI-21 and remove the backstop. So the identity check must run as the table owner, and OD-8's "EXECUTE only on approved projections/services" is realised as EXECUTE on **one gate per approved projection or service**; the role holds no EXECUTE on any projection or service itself.
- Schema and table privileges are re-checked on every execution (ADR 0015 §4, measured), so `authenticated` cannot reach `ops`, and an exposed body that tried to read an `ops` table would fail with `42501`. No gate takes a tenant argument, so holding EXECUTE on it confers no ability to name another tenant. The graph's edges are proven by catalogue pins, because an EXECUTE grant alone is not a runtime boundary.
- **The PostgreSQL 15 constraint.** Changing a function's owner to `ops_operator_api` requires the migration identity to be a member of `ops_operator_api` and the role to hold CREATE on `company_os_api` at that moment. The migration identity is **proven during implementation, not assumed** (the repository's documentation says `postgres`, which is not taken as proof; spike S0.4 measures it). These are PostgreSQL 15 facts; the hosted-readiness step re-derives them for any other version.
- **OD-8a — accepted as a strict, pinned guard exception** (brief §7.6). A pinned exception, never a broad one:
  - **Scope:** one role (`ops_operator_api`), one schema (`company_os_api`), the exact Phase 2C RPC catalogue (names and signatures) and an allowlist of exact migration files, each pinned in the static guard by its full file name: the S2 read-only migration and the S8 acts migration.
  - **Self-contained, exactly pinned migrations; no standing exception** (the owner's pre-push review, which settled the reading the earlier text flagged). Every allowlisted migration, by itself and in order: (1) asserts that it runs as the proven migration identity; (2) grants `ops_operator_api` to that identity; (3) grants CREATE on `company_os_api` to the role, only if its transfers need it; (4) performs only the exact catalogued ownership operations pinned for that file (for S2 and S8, the ownership transfers of the catalogued functions it creates, whose ACL is set before the transfer); (5) revokes that CREATE; (6) revokes the membership; (7) proves the end state (brief §7.6 A, E). Two migrations are acceptable only because each carries the whole lifecycle independently. There is no generic future exemption for `ALTER FUNCTION … OWNER TO`, `CREATE OR REPLACE FUNCTION`, `DROP FUNCTION`, GRANT or REVOKE of EXECUTE, `ALTER DEFAULT PRIVILEGES` (a non-overridable finding in every migration when it names `company_os_api` or `ops_operator_api`, and for any GRANT form with no `IN SCHEMA` clause or with `ops` in its schema list: no default privilege may give `ops_operator_api`, `authenticated`, `anon` or PUBLIC future authority over `company_os_api` or `ops`), any other function ACL change or role membership: a later change to the catalogue or the privilege graph, a rollback included, needs a new forward migration (with its own exact allowlist entry and the full lifecycle where it needs the membership), an explicit static-guard update, reviewed tests, and owner or governance review wherever a capability changes.
  - **Temporary membership:** granted only to the proven migration identity (the guard pins that literal), only inside an allowlisted migration, as its lifecycle steps 2 and 6, with no `WITH ADMIN`, `SET` or `INHERIT` option and no `GRANTED BY`, and revoked in the same migration after its last use; each allowlisted migration asserts that it runs as the pinned migration identity, so every apply proves it. Every other role-to-role grant involving the scrutinised Company OS roles — indeed every other role-membership GRANT — stays unclassifiable and non-overridable exactly as today; every other role-membership REVOKE becomes a non-overridable finding.
  - **Temporary CREATE:** exactly `CREATE ON SCHEMA company_os_api` for `ops_operator_api`, only inside the membership window, bracketing the ownership transfers, and revoked in the same migration. CREATE on `ops`, `public` or any other schema for this role, and any CREATE on `company_os_api` other than the pinned pair, is a non-overridable finding; nothing is left behind.
  - **ALTER FUNCTION … OWNER TO:** allowed only when the destination is `ops_operator_api`, the schema is `company_os_api`, the name and signature are in the catalogue, the statement is one of the transfers pinned for that allowlisted migration file, the migration contains both revoke pairs, and the post-migration tests verify the final graph. Every other `ALTER FUNCTION|ROUTINE|PROCEDURE … OWNER TO` is a non-overridable finding (the catalogue grows only through its pinned literal, never through an override); every other ownership path naming the role (`CREATE SCHEMA … AUTHORIZATION`, `ALTER TABLE|VIEW|SEQUENCE|TYPE|DOMAIN|SCHEMA … OWNER TO`, `REASSIGN OWNED`), any `ALTER ROLE ops_operator_api`, and `SET ROLE`, `RESET ROLE` and `SET SESSION AUTHORIZATION` are non-overridable findings. Every rule of the exception applies at top level, inside a DO body and inside a resolved `EXECUTE` string; a `CREATE ROLE` or `DROP ROLE` naming the role outside an allowlisted migration, or a creating statement without exactly its six attributes, is also a non-overridable finding.
  - **Post-migration proof** (brief §7.6 E): the role's attributes; the migration identity, `authenticated`, `anon`, `authenticator`, `service_role`, `ops_worker` and `ops_gateway` not members; no login role's membership closure containing it; no CREATE on `company_os_api`, `ops`, `public`, any other schema or the database; USAGE on `ops` only where required; ownership of exactly the catalogue; EXECUTE on exactly the gates in `ops` and the pinned list outside `ops`, `pg_catalog` and `information_schema`; no table, column or sequence privilege outside the PUBLIC catalogue reads; the migration's own identity assertion; the measured list of superuser and CREATEROLE roles.
  - **Residual privilege after migration:** ownership of the catalogued functions, USAGE on `ops`, EXECUTE on the gates, and what PUBLIC grants every role. No application or runtime identity can exercise the ownership; only a superuser or CREATEROLE role (the database-owner trust root) could, by first granting itself membership, and in a migration only the pinned OD-8a pair permits that.
  - Every rule is red-tested first. If the pinned exception proves unworkable, the narrowest equivalent (exposing owner-owned gates with a catalogue-pinned graph, which loses the `42501` backstop) needs a separate, explicit owner decision recorded here; it is not adopted by this record.
- **This record authorises no `SECURITY-INVARIANT-OVERRIDE`.** Its only guard change is OD-8a; any override citing ADR 0019 needs a separate owner decision.
- **Residual:** gates and their internal callees execute as the table owner, so isolation inside a projection rests on its tenant predicates and on classifying every emitted reference (the caller's own row, or null for a platform row), proven by the two-tenant matrix and a differential test. An RLS-backed reader role owning the read projections is a recommended hardening; its status before real data is an owner decision.

### 4. Identity and tenancy: explicit membership keyed to the auth user id (OD-3; final confirmation)

- **The principal is the auth user id.** The authoritative human identity is the stable Supabase Auth user id: the verified JWT `sub`, the value `auth.uid()` returns. A membership binds tenant + auth user id (through `ops.principals`, kind `human`) + membership state and role (`tenant_operator`, human principals only by constraint, and, in Phase 2C, at most one active membership per person: a partial unique index, a Phase 2C limit rather than a property of the tenant-generic model). **Same email ≠ same principal:** an email never selects, identifies or authorises a principal or a membership; changing an email never transfers a membership; a new auth user created with a former member's email holds nothing.
- **Email at grant: detection only.** The SHA-256 of the auth user's email at grant is stored and compared only by the owner CLI (`membership list` flags `emailChangedSinceGrant`), as a tamper or change alarm during the temporary coupling to the CRM's Auth directory. The browser path never reads an email. It is **not an authorization boundary**, and no security property is claimed from it.
- **Provisioning.** FORCE RLS, no policy and no grant; written only through `npm run ops -- membership grant|revoke` with the database-owner credential (`membership list` reads), taking the auth user id, never an email. A principal's `(issuer, subject)` and `kind`, and a membership's principal, tenant, role and grant fields, are immutable (ENABLE ALWAYS guards); a change of person or tenant is a revoke plus a new grant. The CRM's owner or administrator state never derives Company OS authority, and no browser-supplied tenant or company id is ever trusted.
- **Tenant eligibility is a temporary Phase 2C policy; the model is tenant-generic.** In Phase 2C a membership is provisioned and enabled only for the tenant that owns the local CRM, because every Company OS member is also a CRM user of that tenant. One eligibility predicate, `ops.membership_tenant_eligible`, called by the grant service and the resolver, applies it; no table constraint, foreign key, trigger or column ties a membership to CRM ownership. Lifting it needs an owner decision that also separates that tenant's Company OS identity from the clinic's CRM trust model (CRM-side separation, a separate Supabase project, or another identity domain), and no data migration; another identity domain also needs the resolver and the grant service to bind the verified JWT `iss` to `ops.principals.issuer` and to check that domain's own session and ban state before PostgREST trusts a second issuer.
- **The resolver**, `ops.operator_scope()`, reads the verified PostgREST claims (`request.jwt.claims`; its `sub` is what `auth.uid()` returns for a PostgREST request, read directly because `auth.uid()` prefers the legacy per-claim setting that the sealed `merge_contacts` pool sets), requires the `authenticated` role and audience, a non-anonymous uuid subject, a live `auth.sessions` row, an existing, unbanned, undeleted `auth.users` row, an enabled human principal keyed to that auth user id and exactly one active membership of an eligible tenant. It returns the tenant and the actor label `principal:<uuid>`. The tenant comes **only** from the membership; every id the browser sends is a selector resolved inside that tenant, and a foreign id is answered exactly like a missing one. UI acts carry the source `company-os-ui`. The owner CLI refuses a typed `principal:` actor in TypeScript; the SQL still accepts any well-formed label from the owner credential, so the label identifies a gate-resolved caller only on application paths.

### 5. Two browser mutations, and only two (OD-4, OD-6; final confirmation)

- **(A) Decide an existing review** — accept, reject or needs_edit, through `ops.record_review_decision` with the resolved tenant, `principal:<uuid>` and `company-os-ui`. The existing semantics hold unchanged: final once, OS409 on a change, OS403 on accepting a do-not-contact item, OS404 for a foreign item. **Accepting a review is not a send** (REVIEW ACCEPTANCE ≠ WHATSAPP SEND): it writes no outbound row and no job; a send stays the explicit CLI act of ADR 0018 §4, with its own eligibility re-check. **What a browser decision means** (the owner's pre-push review, which accepted the draft's exclusion from the browser): it decides the **structured triage review** (the review item and, where shown, its structured advice), never the exact outgoing WhatsApp message or the hidden reply draft; it does not authorise a WhatsApp send, because an accepted review is only one precondition that the later, separate, deliberate `messaging -- send` requires, alongside its own eligibility re-check; and no UI label, confirmation, status or fixed error text, audit row or event presents it as a message, draft or reply approved for sending (the act writes exactly the existing `lead_triage.reviewed` event with the decision). The browser never shows the reply draft (Decision 6), so a browser acceptance is made without reading the text a later send transmits; `messaging -- send` never displays it either (SI-52), so the only reading of the draft before it leaves is the send operator's `npm run ops -- triage show`, the existing owner CLI path, which the amended SI-39 names; that reading is expected and not enforced (a recorded residual, Consequences), and another safe draft-review surface needs a future explicit owner decision. The review semantics support this act without new authority: the gate only binds the resolved tenant, actor and source.
- **(B) Trip an execution stop** at tenant, company, department or agent scope inside the caller's tenant, with a required reason, always through `ops.trip_execution_stop` and its platform-wide exclusive lock, with no pre-check (a pre-check could report "already stopped" while a concurrent clear commits, which would break deny-wins). Deny-wins, serialisation with run admission, audit and origin are preserved: the recorded origin is `owner` (the non-system origin: a person) and the actor `principal:<uuid>`. The outcome (`stopped` or `already_stopped`) follows the CLI's own test. `global` and `job_kind` scopes are refused. **The request must be bounded:** the trip gate carries a pinned `lock_timeout` inside PostgREST's statement timeout, so the API never hangs (whether `lock_timeout` bounds the advisory-lock wait inside `trip_execution_stop`, and the statement timeout itself, are NOT MEASURED: spike S0.4, M4 and M11; if the bound cannot be shown, the phase stops for owner review); on contention or timeout it answers one generic, retryable refusal that reveals no other tenant, job, execution state or timing beyond the bound, and creates nothing. The UI shows "Stop request could not be completed yet. Retry." and never shows a stop as created before the database commits it. Driver-backed tests exercise lock contention.
- **Disabled until the prerequisite.** Both act functions are created only by a second migration written after the `users` edge function's user-management prerequisite (the `patchUser` authority and ordering issues and the `createSale` half-state) is fixed and tested. Before then no migration creates them and no database holds them at rest (planning prototypes run only inside rolled-back transactions); a frontend feature flag is never the boundary, and the act surface does not reach hosted production prematurely.
- **Nothing else.** The browser never clears a stop, sends, resends, retries or marks a send, creates or activates a channel (the production gate stays closed), records a price, sets a limit, requests or retries a run, recovers a job or review, changes an organisational unit, mutates the CRM, or changes security or governance configuration. Those stay CLI or operator-backend acts.

### 6. Minimised, tenant-scoped projections (OD-5, OD-7; final confirmation)

Every read is an explicit-column projection. No output carries another tenant's data, a stored message or task body, a stored phone number, a reply draft, a run result, a raw job error, a provider secret or internal id, a global sequence value (`events.seq`, `job_events.id`: this reader is the SI-26 review event) or a platform-wide identifier. No output carries an identity or email field either: no Auth or CRM email, no email hash, and no raw free-form actor label; the stored reviewer, `requested_by`, `tripped_by`, `cleared_by`, `marked_by`, `configured_by`, `set_by`, `ended_by` and `recorded_by` values and a principal's display name are free-form and are omitted, with no replacement identity field in 2C, and an event's source passes only through a pinned provenance allowlist (PR #6 architecture review; brief §9, §13). Free-text content a read returns (a decision note, a stop reason and clear reason, the advice summary and recommended next action, and the tenant's own owner-typed configuration labels: tenant, company, department and agent names and a channel label) is content, not identity, and is not claimed free of email-like text; it is synthetic or test only in 2C. Platform state is limited to one derived boolean, `globalAdmissionBlocked`, plus the pinned effects a platform stop or the global ceiling can have on the tenant's own rows (for example a run held or refused), which carry no platform id, amount, count, reason, actor or time; every reference to a platform-scoped row is null. No global ceiling amount, global spend, platform stop row or price row reaches the browser, and a new platform field needs an owner decision.

The structured review advice — for `lead_triage`, its classification enums, summary and recommended next action — is visible only on an explicit open of one review, through a capability-pinned projection (only `lead_triage` in this phase), only for a task admitted as `synthetic` or on a channel in `test` mode at call time, never in a list, never in durable browser storage (`no-store`, memory only, `gcTime: 0`), and never as a generic content viewer. **It never includes the reply draft**, the stored inbound body or any task description, the sender's stored number, a secret, an access token or a raw provider error; its summary and recommended next action are model-written from the message and may echo its words, which is why it is limited to synthetic or test origins. No list carries any field of the model's proposal.

### 7. Screens, browser handling and mutation ordering (OD-9, OD-10, OD-11)

Eight core screens: Overview, Activity, Tasks, Agents, Agent Runs, Reviews (the Reviews / Decision Queue, never a send-approval queue), Execution Stops, Costs. Communications is optional and only as a narrow status view of counts, with no authority and no message list. The UI shows "working" only for a running AgentRun whose job holds a live lease, with the run's id as evidence.

MFA and a production CSP do not block synthetic 2C. Phase 2C includes: no provider or database secret in any bundle (`scan:build` learns the new names), no Company OS content in `localStorage`, `sessionStorage`, IndexedDB or Cache Storage, `Cache-Control: no-store`, safe session expiry, explicit sign-out that clears the cache, and no analytics receiving operator content.

Read-only screens ship first; the two mutations follow only as Decision 5 allows.

### 8. Local and test first, synthetic and test data only (OD-12, OD-15)

The surface runs on local and test stacks only, over synthetic and test data only: no real patient data reaches it while Q8 is open and the production real-data gate is closed (ADR 0018 amendment 1). A hosted operator surface or any real data additionally requires a separate readiness step with a blocking verification, the user-management prerequisite, session hardening, an MFA decision and implementation, a CSP, a hosted exposure review and every Phase 2B gate; no production deployment is approved. No new third-party dependency, always-on process, origin, login role or public generic API is added. Notifications are deferred (OD-13).

### 9. Invariants and guards move with the surface

- **Proposed new invariants** (brief §15; numbers re-verified at implementation, SI-54 and above being unused at `d1819f25`): SI-54 the API surface and capability graph; SI-55 identity (the auth user id, never an email) and membership derivation; SI-56 tenant isolation and minimisation (no reply draft; no identity email or raw actor label, with owner-typed configuration labels classified as content, narrowly extended at the PR #6 review); SI-57 truthful working state; SI-58 browser authority (the two acts, acceptance ≠ send, trip-only, bounded contention, no channel activation); SI-59 browser handling (no durable storage, no bundle secret).
- **Amended by owner decision, approved in principle (final confirmation, 2026-09-22).** Each changes only as far as Phase 2C requires, and every other clause stays word for word, except the current-state corrections the owner's pre-push review of the exact wording required (SI-21; SI-39's act allowlist) and one that follows directly from them (SI-39's print clause, which now names `triage show`'s existing display of the stored proposal, owner-approved on 2026-09-22 as existing owner-CLI behaviour, not new authority); the review left SI-15 and SI-52 as drafted. The final, owner-approved texts, which S1 writes verbatim into `supabase/tests/securityInvariants.test.ts` and then `docs/SECURITY_INVARIANTS.md` (any later wording change returns to the owner):
  - **SI-15:** "The ops schema is unreachable by anon and authenticated, is absent from the PostgREST allowlist, and no PostgREST request reaches it with any credential, service_role included, with one exception: an authenticated request to a pinned company_os_api function, which runs as the NOLOGIN role ops_operator_api and enters ops only through that function's identity-and-membership gate (SI-21). The exception grants anon, authenticated and service_role no privilege on ops; anon and authenticated still hold none, and service_role keeps only its pinned USAGE on ops and EXECUTE on ops.enqueue_job."
  - **SI-21:** "Company OS data is backend-only except for the gated browser outputs below, and direct Company OS authority stays with the database owner: no application role (anon, authenticated, service_role, ops_worker, ops_gateway, and so no browser, PostgREST or runtime login acting as one of them) and no capability role (ops_operator_api) holds any privilege on a Company OS table, any grant on all tables, sequences or functions in ops or default-privilege grant there, or EXECUTE on a Company OS service, and every Company OS service is SECURITY INVOKER. Company OS tables and services are otherwise reached only through pinned SECURITY DEFINER capabilities, never a generic one: no ops function is executable by PUBLIC, the only SECURITY DEFINER functions in ops that ops_worker, ops_gateway or ops_operator_api can execute are, respectively, the worker's lease-bound capabilities and runtime functions, the gateway's two functions bound to a configured provider target, and exactly one identity-and-membership gate per catalogued company_os_api operation, and service_role's only one is ops.enqueue_job. ops_operator_api is a NOLOGIN capability role, not a human or application principal: it owns only the catalogued company_os_api functions, and at rest it has no members and is in no login role's membership closure. authenticated holds nothing in ops, executes in company_os_api only those catalogued functions, each of which runs with ops_operator_api's privileges and calls only its own gate, and never becomes ops_operator_api: it is not a member of it and cannot switch to it. Company OS data reaches the browser only through those gates and only as their pinned minimised outputs, and through them an authenticated Company OS member can at most read its own tenant's pinned projections, record a decision on one of its own tenant's reviews through ops.record_review_decision, and trip a stop at tenant, company, department or agent scope within its own tenant through the authoritative ops.trip_execution_stop; clearing a stop remains a recorded owner act through the owner CLI (SI-31), and no global, system or job_kind stop can be tripped from the browser."
  - **SI-39:** "The operator view is read-only by default and backend-only: its read commands run inside read-only transactions over the owner connection, it reads no environment variable but ADMIN_DATABASE_URL and never a provider key or a routing variable, it never prints a result, prompt, task or agent text, idempotency key or connection string, except that triage show prints the stored proposal, reply draft included, of the one review item it names, and it withholds any key-shaped value a worker published. It changes state only through an explicit allowlist of acts: recording a price version, setting or retiring a spend limit, recording a review decision (triage accept, reject or needs-edit), opening the missing reviews of succeeded runs from their stored results (triage recover) and, from Phase 2C, granting or revoking a Company OS membership; every other command is a read, and no further act exists without a reviewed extension of this invariant. The membership commands (grant, revoke and list) have no option that takes an email, grant identifies the person only by auth user id, and they never print an email, an email hash, an auth token or privileged connection information."
  - **SI-52:** "Message content lives where the work needs it and nowhere else. An inbound body is stored only as its task's description, which is what an agent run reads; a reply draft only in the model's stored result and the review derived from it, read at the moment of sending and copied nowhere. No event, outbound row, gateway log line or messaging tool output carries a body, a draft, a sender's number or a secret, and a refused message leaves only its channel, its conversation and a reason. Phase 2C adds one read: on an explicit open of a single review of its own tenant, a Company OS member may read that review's capability-pinned structured advice (for lead_triage, its classification enums, summary and recommended next action), only for a synthetic or test origin, into browser memory under no-store and nowhere else; the projection never includes the stored inbound body or any task description, the sender's stored number, the reply draft, a secret, an access token or a raw provider error, and because its summary and recommended next action are written by the model from the inbound message and may echo its words, the read is limited to synthetic or test origins."

## Alternatives

- **Owner-owned exposed wrappers** (the brief's first recommendation). Simpler, and needs no guard extension. Rejected by the owner's OD-8 amendment: the exposed layer would run as the table owner, so a wrapper bug could read any table; the dedicated role makes that fail with `42501`. It remains only as the fallback if the pinned exception proves unworkable, which needs a separate owner decision; a gate or projection defect still runs as the owner in either design.
- **Membership keyed to an email.** Rejected by the owner: an email can be changed, including by a CRM administrator today, and the same email is not the same principal.
- **Membership restricted to the CRM-owning tenant as a data-model constraint.** Rejected by the owner: the restriction is a temporary Phase 2C eligibility policy, and the model stays tenant-generic for future non-CRM or independently isolated tenants.
- **A separate Vite entry or an npm workspace.** Equal on security; more build and publish wiring. Kept only as the S0.1 fallback.
- **Routes inside `CRM.tsx` (`CustomRoutes`).** Couples the surface to ra-core and edits a registry-listed file. Rejected.
- **A loopback owner console running as `postgres`.** Conflicts with ADR 0015 §4 and puts the owner credential behind a browser. Rejected.
- **A hosted engine HTTP process or Edge Functions reaching `ops`.** A new internet listener, a new credential, and (for Edge Functions) the sealed owner pool must reach nothing in `ops` (SI-27). Rejected.
- **Exposing `ops` read-only with RLS for `authenticated`.** Exposes rows rather than projections and turns every future column into a disclosure decision. Rejected.

## Consequences

- The only Data API path into Company OS data is the pinned `company_os_api` graph. `ops` is never exposed.
- In Phase 2C, Company OS members exist only for the tenant that owns the local CRM; the membership model itself stays tenant-generic.
- **CRM-admin account capture (owner decision).** Company OS authority keeps today's trust root, the database-owner credential, which alone can mint a member. But CRM administration can capture an existing member's login (any CRM administrator through `patchUser`, the active CRM owner included, until the user-management prerequisite fixes both its ordering and its authority, and anyone holding `service_role`, the JWT signing secret or Auth administration). The principal being the auth user id means an email change never retargets a membership to another subject, but it does not stop a takeover of the same subject. The risk is **accepted only for local, synthetic and test Phase 2C**; real data and any hosted operator surface are **blocked** until the `users` edge function's `patchUser` and `createSale` authority and ordering issues are fixed and tested, so that no CRM administrator, the active CRM owner included, changing profile or user information can retarget or acquire another person's Company OS principal. The `email_at_grant` alarm is detection only, and `membership revoke`, not CRM disable, is the Company OS revocation.
- **Token theft (owner decision).** Membership limits what a valid principal may access; it does not prove a token was not stolen. A stolen member token can read that tenant's (test) projections, open the advice, decide pending reviews and trip stops in that tenant; it cannot send, clear, configure a channel, touch money, reach platform scope, read a reply draft or read another tenant. Ordinary Supabase authenticated-session risk is accepted for synthetic and test development only; before real patient or production operator use, session hardening, an MFA decision and implementation, a CSP, a hosted exposure review and auth and user-management hardening remain required. A CLI send does not show who accepted the review whose draft it transmits; showing the reviewer and source in the send itself is recommended.
- **Unread draft (a consequence of the SI-52 amendment; recorded for the owner, not decided).** A browser acceptance decides a review whose reply draft the acceptor cannot see (Decision 6); by the semantics the owner recorded at the pre-push review, it approves the structured review, not the draft, and authorises no send (Decision 5). `messaging -- send` transmits that draft without displaying it (SI-52). The send operator is expected to read it with `npm run ops -- triage show` before sending, but nothing enforces that, so a model-written draft whose review was accepted in the browser can leave with no person having read it. The owner accepted the draft's exclusion from the browser; that nothing enforces the reading stays recorded, not decided.
- **Kill-switch contention (owner decision).** The serialised behaviour is accepted: every trip takes the platform-wide kill-switch lock, so a member tripping in a loop can delay other tenants' leases, and a trip's lock wait is a timing signal about their activity. The bounded request caps a trip's own lock wait, and so the timing it can reveal, and the generic retryable refusal does not say who holds the lock; neither caps how much a loop of trips delays other tenants, which spike S0.4 measures (M4) when it fixes the bound.
- `synthetic` and `test` are owner-asserted labels, not proof of content (the Phase 2B residual): connect only test numbers carrying test data.
- The CLI remains the full operator surface; removing `company_os_api` from the exposed schemas turns the UI off instantly with nothing in `ops` changed (assuming pg_graphql does not reflect the schema, M1).
- Nothing here opens the production real-data gate, decides Q8, approves the PUBLIC CRM helper grants (ADR 0018 amendment 3), changes the Meta live-probe requirement or adds Jev (decision P; Phase 2D).

## Rollback

Remove `company_os_api` from the exposed schemas (instant); revoke a membership (per person, next call); or, by a new owner-approved forward migration that the S2 and S8 entries do not cover (its own exact OD-8a allowlist entry, a static-guard update and reviewed tests, running the lifecycle of Decision 3 itself): revoke USAGE on `company_os_api` from `authenticated` (the effective cut-off, needing no membership); inside its own membership window, revoke EXECUTE on the exposed functions and drop them; then revoke EXECUTE on the gates and USAGE on `ops` from `ops_operator_api`, drop the gates and the role, and assert the ACLs. The principal and membership tables and the indexes are additive. The `src/App.tsx` switch reverts in one change; `<CRM/>` was never edited.
