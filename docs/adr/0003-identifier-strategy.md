# ADR 0003 — Identifier strategy at the CRM seam

**Status:** **Accepted** (owner decision 2026-09-13, as reconciled in the 2026-09-13 addendum) · **Date:** 2026-09-10 (reconciled and accepted 2026-09-13)

## Context

Every CRM id is `bigint generated by default as identity`. No uuid-generating extension is declared (`01_tables.sql:7-8` declares only `http` and `citext`); the only uuid in the schema is `sales.user_id`. Agents need client-generated ids so that inserts can be made idempotent.

## Decision

**UUID/ULID primary keys on all engine tables. No foreign key from an engine table into `public.*`, ever.** The CRM is referenced as `(crm_provider, crm_entity, crm_id)` text.

## Alternatives

- **bigint FKs into `public.*`.** Rejected: one such FK silently welds Atomic CRM to the core and makes "replaceable adapter" a slogan.
- **Engine bigints.** Rejected: not client-generatable, so idempotent inserts need a round-trip.

## Consequences

- Cross-boundary joins are application-level, not SQL-level. Accepted — that is the price of a replaceable CRM.
- Referential integrity across the seam is the adapter's job, including handling a CRM record that has been deleted underneath it.
- ~~Requires `pgcrypto` or ULID generation in application code.~~ *(Corrected 2026-09-13: false when written. PostgreSQL 15 ships `gen_random_uuid()` in core, and the engine's uuid keys use it with no extension, so the next sentence has nothing to declare; see Extensions in the 2026-09-13 addendum.)* Declare it in the declarative schema — unlike `pg_net` and `pgjwt`, which exist only in migrations and are therefore invisible to `db diff`.

## Addendum 2026-09-13 — reconciled with the implementation, ADR 0012 and ADR 0015 (after Phase 1C)

This record was re-read against Phases 1A–1C, against [ADR 0012](0012-worker-tenant-context.md) as accepted, and against [ADR 0015](0015-company-os-domain-core.md) with its owner addendum. The one false claim is struck above. **Status stays Proposed**, pending the owner's review of the reconciled Decision below and one open question. *(Accepted by the owner on 2026-09-13 as reconciled below; the open question was decided the same day.)*

### As built

**Keys.**

| Table | Primary key |
| --- | --- |
| `ops.tenants`, `jobs`, `companies`, `departments`, `agents`, `tasks`, `events` | `uuid`, server default `gen_random_uuid()` |
| `ops.job_events` | `bigint` identity (an execution trail) |
| `ops.task_jobs` | composite `(tenant_id, job_id)` (a link) |
| `ops.worker_instances` | `text` `worker_id` (fleet infrastructure, no `tenant_id`) |

No ULID exists. `public.*` keeps its key strategy: every table has a `bigint` identity key, including those added since this record was written (`acquisition_attributions`, `lead_profiles`, `loss_reasons`, `inbound_emails`). The one exception is `public.configuration`'s `integer` singleton (`check (id = 1)`), and `sales.user_id` is still its only `uuid` column.

**No entity id is client-generated.** No `ops` function that creates a tenant-scoped row accepts that row's id. The exception is fleet infrastructure: `ops.worker_instances` is keyed on `worker_id`, which the worker process chooses (`OPS_WORKER_ID`, or `hostname:pid:random` in `engine/worker/main.ts`), and `ops.worker_heartbeat` upserts the row under it. `worker_id` carries no tenant: it names the lease holder, and the tenant is re-read from the leased job row it owns (ADR 0012). Callers also choose values that are not row keys: slugs (unique per tenant or per company), idempotency keys, the event `source`, and `correlation_id`, which the domain functions accept and `ops.events` stores unvalidated. `subject_id` and `causation_id` are caller-supplied too, but must resolve inside the event's company.

**Idempotent creation is by key, not by id, and exists only for jobs.** Status setters and `assign_task` are no-ops when the row is already in the target state; `transition_task` is too for a non-terminal target, but a retry to a terminal status raises `OS409`.
- `ops.enqueue_job` deduplicates on `(tenant_id, kind, idempotency_key)` and returns the existing job.
- `ops.request_task_execution` namespaces the key as `task:<task_id>:<key>` and refuses (`OS409`) a job the task did not request.

The Company OS create functions are not idempotent. A retried `create_company`, `create_department` or `create_agent` fails on its unique slug (`23505`); a retried `create_task` or `record_event` inserts a second row.

**References.**
- A uuid is globally unique but is not, by itself, the key one Company OS row references another by. References between Company OS rows go through composite foreign keys that carry `tenant_id`, and `company_id` where the target is company-scoped; the migration's end-state assertion checks that each exists, by name. The other route is an insert guard, for `events.subject_id` and `causation_id` (ADR 0015 §3, SI-22). `events.correlation_id` is neither: it is stored as given. `ops.job_events.job_id` (Phase 1A) references `ops.jobs(id)` alone, and its `tenant_id` references `ops.tenants(id)` separately.
- No engine table has a foreign key into `public.*`. No static guard enforces it yet.
- One SQL-level capability crosses the seam: `ops.purge_inbound_email_ledger` (Phase 1B), a SECURITY DEFINER function callable only under a live lease whose tenant has `owns_local_crm`. It deletes `ingested` and `failed_permanent` `public.inbound_emails` rows older than a retention window with a 30-day floor (SI-18). It creates no foreign key and joins no `ops` row to a `public` row.
- `(crm_provider, crm_entity, crm_id)` is **not built**. The only CRM binding is the tenant-level `owns_local_crm`.

**Extensions.** Nothing needs declaring. `pg_net` was dropped (`20260911235500_drop_pg_net.sql`), and `pgjwt` is still migration-only. `ops` is written as hand-written, self-asserting migrations outside `supabase/schemas/` and `schema_paths`; reconciling that is [ADR 0006](0006-declarative-schema-workflow.md)'s decision.

### Premises that no longer distinguish the options

"Agents need client-generated ids so that inserts can be made idempotent" and "Engine bigints. Rejected: not client-generatable" no longer separate uuid from bigint: `ops` uuids are server defaults, and idempotency is key-based. What does separate them is tenancy: a key drawn from one identity shared by all tenants reveals cross-tenant volume through its gaps, which is why ADR 0015 owner decision 5 makes `ops.events.seq` internal only.

### The Decision, reconciled (proposed for acceptance)

1. **Engine entity tables have server-generated uuid primary keys.** Trails, links and fleet infrastructure may use other keys; whether a shared identity on a trail may ever reach a tenant is the open question below. A key is never a source of tenancy. *(Decided 2026-09-13: a shared identity on a trail never reaches a tenant; see below.)*
2. **No foreign key from an engine table into `public.*`, ever.** Unchanged.
3. **The CRM is referenced as `(crm_provider, crm_entity, crm_id)`, always tenant-scoped.** When it is built:
   - it is stored on a row that carries `tenant_id`, and `company_id` when company-scoped, under ADR 0015's composite keys;
   - the tenant comes from a lease or a membership, never from an argument, the reference, a payload or model output (ADR 0012; ADR 0015 §4);
   - `crm_id` is unique only within that tenant's CRM;
   - a `crm_entity` naming the CRM's customer accounts means the adapter's entity (for Atomic CRM, `public.companies`), never `ops.companies`;
   - tenant-wide work resolves it only through the leased tenant's `owns_local_crm` (SI-18). Company-scoped work resolves it only through a company-level binding. None exists, so no company-scoped capability may resolve a CRM reference today;
   - an event carries the reference, not the referenced content: no message bodies, notes, emails, clinical information or sensitive CRM records, unless a future event type explicitly requires such content and its retention and security policy has been defined first (ADR 0015 owner decision 6). A reference recorded in `ops.events` cannot be repaired, so its consumers must tolerate one that dangles.
4. **Idempotency uses tenant-scoped keys, never a trusted caller-supplied id.** A caller-chosen idempotency key, slug, correlation id or entity id is data, never authority: it grants no scope, and a uniqueness conflict must not reveal another tenant's row. The owner and `service_role` stand outside the boundary (ADR 0015 owner decision 7) and pass an explicit tenant today (ADR 0015 §4; `ops.enqueue_job`). For every other caller, no caller-chosen value selects scope except through a server-recorded binding: a worker's `worker_id` and the job id it names, checked against a live lease (ADR 0012), or a future membership. Any Phase 1D path that creates tasks or records events needs such a key.

### Open, for the owner (decided 2026-09-13)

- **`ops.job_events.id` is also one identity across tenants**, and `ops_worker` can read it under the lease-bound policy. No tenant-facing reader of it exists. Owner decision 5 names only `ops.events.seq`; whether it also covers `job_events.id`, and any future identity shared across tenants, is undecided. **Decided 2026-09-13 (owner):** yes. Decision 5 extends to `ops.job_events.id` and to any future global monotonic sequence: they are internal only, and must not become tenant-facing cursors, pagination offsets or tokens, event positions, counters or activity indicators (ADR 0015 owner clarification, SI-26). The `job_events` bigint key stays as it is.
