# Security invariants

**The executable list is [`supabase/tests/securityInvariants.test.ts`](../supabase/tests/securityInvariants.test.ts). This document is its index, and a test fails if the two drift.**

Read this before changing anything under `supabase/`, `src/components/atomic-crm/providers/`, or a deployment path (`deploy.yml`, the makefile, `scripts/`). Each row names a property the system must hold and the guard that actually proves it — not a guideline.

---

## The rule that produced most of the others

> **DECLARATIVE SCHEMA != automatically trusted migration output.**

`supabase/schemas/*.sql` is a declaration of intent. `supabase db diff` turns it into a migration, and the migration is what reaches a database — **they are not the same thing, and the difference has been a live security hole three times**:

| Declared in the schema | Emitted by `db diff`? | What happened |
| --- | --- | --- |
| `with (security_invoker = on)` on views | **No** — reloptions are never emitted | Two views were recreated as owner-executing, and `anon` could read every contact record over plain HTTP |
| `alter default privileges … revoke … from anon` | **No** — not DDL it can emit | Three new tables were born with `GRANT ALL TO anon` |
| `update storage.buckets set public = false` | **No** — DML | The attachments bucket stayed public in every migrated database |

Every generated migration is reviewed before it is accepted. Run `supabase db diff` deliberately, read every statement, and add a hand-written migration for anything the generator cannot express — with a `raise exception` block asserting its own end state, because a migration that silently no-ops is worse than none: it looks applied.

**The current `db diff` output is not empty and must not be applied unreviewed.** It emits `create extension pg_net` and recreates three views without `security_invoker` — regressing SI-01 and SI-02 together.

## Caveats that matter more than the table

- **SI-06 is an ACCEPTED RISK, not a satisfied invariant.** The edge functions run as `service_role` today. Both database suites assert that bypass **explicitly**, so a green RLS run can never be mistaken for worker isolation. Closing it is [ADR 0012](adr/0012-worker-tenant-context.md)'s integration work; that ADR was accepted on 2026-09-12 and moved the worker off `service_role` (SI-16), while the edge functions remain on it. *(2026-09-13: one edge function is different. `merge_contacts` pools a `postgres` login and assumes `authenticated` for each transaction; SI-27 proves that channel reaches nothing in `ops`.)*
- **SI-11: RLS does not gate `TRUNCATE`.** Measured: as `anon`, `truncate public.lead_profiles` took it from 2 rows to 0 while every SELECT policy was in force. A grant is not made safe by RLS.
- **SI-02 is irreversible in one direction.** Reinstalling `pg_net` re-grants `anon` and `authenticated`, and no privilege change this project can make will close it again — the `net` schema is owned by `supabase_admin`, and only a grantor may revoke. Removal was the only containment available.
- **SI-14 is bounded, and the bound matters.** GUCs are readable and writable by any role, so no GUC-transport design is unforgeable against a fully malicious worker *process*; against one, the bound is `ops_worker`'s grants. What binding tenancy to a live lease *does* defend against is a worker bug that forgets the context, a worker that takes the tenant from the **payload**, and — from Phase 1B — LLM output reaching the tenant decision. The payload is the untrusted surface; tenancy is now unreachable from it.
- **SI-13 and SI-15 do not make the worker trusted.** They make it *small*: it reads, it is granted twenty pinned `ops` function signatures (it calls eighteen), five of which check no lease (the fleet heartbeat pair, the lease reaper, the stale agent run sweep and, since Phase 1D.1, the spend ceiling sweep), and it holds no privilege in `public`. *(2026-09-14: eleven until Phase 1D added the six agent run capabilities. 2026-09-17: seventeen until Phase 1D.1 added `job_execution_stop`, `defer_job` and `enforce_spend_ceiling`. Owner review 2026-09-17: these counts are of granted signatures; earlier text said the worker calls them all.)*
- **SI-16 is why a deployment mistake is loud.** `ops_worker` is NOLOGIN and carries no credential, so a real deployment must create a login role (`scripts/provision-worker-role.mjs`). That role is NOINHERIT and holds nothing directly: it reaches every privilege by assuming `ops_worker` for one transaction. Delete that `set local role` and the worker fails with "permission denied for schema ops" instead of quietly running with whatever the login role happened to carry.
- **SI-18 is the shape every later capability must copy.** The handler receives a capability, never a database client — it cannot name the rows, cannot choose the tenant, and cannot widen the window. This is the earliest form of the Tool Gateway; it is deliberately not that yet.
- **SI-03 became a mechanism on 2026-09-13.** It used to be a decision backed by a validator. The generic MCP SQL function is now removed, and `scripts/production-scope.mjs` refuses the plausible ways back: an unreviewed function directory or a second functions tree; function configuration away from its canonical paths, or a module map or package manifest it does not read; an import outside the tree, of an unreviewed module, or by a computed name; a known MCP server or SQL parser; a raw SQL call the parser can name given anything but a literal, so a value travels as a bound parameter; the shared Postgres pool outside `merge_contacts`, or a function importing another function's files; and a function deploy outside `deploy.yml` and the makefile, one not naming reviewed functions, or one that two blocking checks do not precede. The second check asks the target project which functions it serves (`--project-ref` in CI, `--linked` in the makefile) and refuses any outside the allowlist, `mcp` included; the deploy that follows must run under the same plain condition and reach the same project: a named deploy never deletes a function, and this check deletes nothing either, so an unexpected function waits for a person. It reads JavaScript and TypeScript with the TypeScript parser, because three adversarial reviews got past its earlier versions; each bypass they found is now a test. Out of reach, deliberately: a person at the CLI; a command or module name assembled where no literal shows it; a raw method reached through a computed member name or reflection, which is why SI-27 seals the owner-session files; SQL through a method other than the raw ones it names, or caller-chosen identifiers handed to a query builder; code outside `supabase/functions`, such as an engine module or a database function running dynamic SQL; and a function deployed after the hosted check runs. The decision it records is unchanged: agents get explicit operations, never SQL.
- **SI-07 is retired (2026-09-13).** It said the SQL read path was read-only in the database itself, not only in the parser. Its only subject was the MCP function's `query` tool, removed with the function; SI-03 now holds the stronger property that no such path exists. The id is not reused.
- **SI-19 removed a feature, not just a leak.** Upstream's mobile "offline mode" was a React Query persister writing every viewed record to `localStorage` for 24 hours. No product document for this tenant asks for offline access, so it was removed rather than allow-listed. A screen already open still survives a dropped connection; nothing survives the tab. The legacy key is purged at startup because nothing else would ever expire it. **Not covered:** list filters the user types (ra-core's store keeps them until logout, SEC-1BS-13), and a cache someone might add inside the Supabase provider, which the storage test does not render.
- **SI-20 makes the publish scan, rather than checking that a scan runs.** Its first shape checked that a CI step scanned before each publish, and an adversarial review broke it within the hour: `make`, npm scripts, `--dist` and Pages actions all published unscanned. Every GitHub Pages publish now goes through `scripts/publish-pages.mjs`, and any other invocation of gh-pages is a violation.
- **SI-20 cannot see the dashboard.** No Supabase CLI command uploads signing keys, so the only way a hosted project comes to trust the development key is a person importing it. The repository rules cannot observe that; the deploy-time check asks the project's own JWKS endpoint instead, for the same ref `supabase link` uses, and treats "could not ask" as a failure. It runs per deploy, not continuously. *(2026-09-13: the push rule now also reads a version-pinned or flag-prefixed CLI, such as `supabase@2.117.0` or `supabase --debug`, and counts a check as blocking only when every `continue-on-error` is statically false; an expression counts as true.)*
- **SI-21 is a privilege boundary, not an RLS one.** In Phase 1C nothing but the owner reads or writes Company OS data. The lease-bound read policies on those tables exist with no grant behind them; they are proven through a grant that lives inside a rolled-back transaction, which is evidence of their shape for a future reader and nothing more. And PostgreSQL gives every new function EXECUTE to PUBLIC — the Phase 1A per-schema default-privilege revoke does not remove that (measured) — so the pinned EXECUTE set in `company_domain_core.sql` is what catches a function someone forgot to revoke.
- **SI-22 and SI-23 stop at the owner.** `postgres` can `DISABLE TRIGGER`, and on Supabase it can set `session_replication_role = replica`, which skips foreign-key checks and ORIGIN triggers. The UPDATE-path guards are `ENABLE ALWAYS`, so replica mode does not silence them; insert validation and foreign keys are not. That is the same line SI-06 draws for BYPASSRLS.
- **SI-22 does not make a company an isolation boundary.** Tenant is the boundary. A company is an organisational partition inside it; two businesses that must not see each other are two tenants.
- **SI-23's provenance and reserved-namespace checks are tripwires.** Any role can write a GUC and only the owner holds DML, so they stop an owner-side code path that forgot to declare what it is doing — not an attacker.
- **SI-23's guards are only as present as their triggers.** The static guard rejects a migration that disables, downgrades, drops without re-creating, replaces without re-enabling `ALWAYS`, or CASCADE-drops an `ops` trigger. It does not read function bodies: a `create or replace function` that turns a guard into a no-op leaves every trigger in place, and only the SQL suites, which exercise each guard, catch it.
- **SI-24 holds under concurrency, not only in sequence.** The bridge never calls `ops.enqueue_job`, whose idempotent path returns whichever job holds a key. The Phase 1C adversarial pass measured, with two connections, a `service_role` enqueue under a task's namespaced key landing between the bridge's check and its enqueue, and being adopted. The bridge now inserts its own job and refuses the unique violation, and `engine/domain/companyOs.dbtest.ts` runs that race.
- **SI-15 covers the Data API, not every door on a local stack.** The probe attacks REST and GraphQL with five credentials, each behind a positive control, and asserts the live PostgREST search path excludes `ops`. It holds no signed-in `authenticated` JWT. On the local CLI stack, three unauthenticated paths run SQL as `postgres`: Kong `POST /pg/query`, Studio `POST /api/platform/pg-meta/default/query`, and Postgres with the default password. Docker Desktop publishes all three on every interface, IPv6 included, unless its Port binding behavior is "Localhost only" (measured 2026-09-12). That is a development-machine exposure this invariant does not cover; `npm run check:local-exposure` detects it (see SECURITY.md §9).
- **SI-25 keeps a development tenant out of production.** `supabase/seed.sql` creates a `dev` tenant with a company, departments and agents, and until 2026-09-13 `scripts/supabase-remote-init.mjs` pushed it to every new hosted project. Local stacks and CI still seed on purpose. The guard also refuses a changed seed path, including an inline or per-remote seed table, a seed file named outside four reviewed local lines, and a glob that can expand to one (`supabase/*.sql`, `**/*.sql`, `se?d.sql`). *(2026-09-13, owner decision on reference data:)* the seed's datasets are classified. `favicons_excluded_domains` is global reference data and ships in migration `20260913120000`, additive and idempotent; CI replays migrations without the seed and `supabase/tests/referenceData.mjs --without-seed` proves every reference domain is there and no tenant data is. `loss_reasons` is tenant vocabulary (CLAUDE.md rule 2, ADR 0013): it stays in the local seed and waits for an explicit onboarding path, so a hosted tenant cannot mark a deal lost until that path exists. The `dev` tenant and its Company OS rows are local data only. Out of reach: a person seeding by hand, a command or path assembled from string fragments, a directory-wide glob such as `supabase/*`, and a seeded local database dumped and restored elsewhere.
- **SI-26 guards grants, not what code does with a value.** `ops_worker` reads `ops.job_events.id` under the lease-bound policy and is not tenant-facing. A worker capability, edge function or future API that reads a global sequence through `ops_worker`, `service_role` or the owner and returns it to a tenant is outside the guard, and is a review event under ADR 0015's owner clarification. Before any tenant-facing event or job-event reader exists, a tenant-scoped or opaque cursor must be designed. `ops.job_events` keeps its bigint key.
- **SI-27 is containment by code, not by role.** `merge_contacts`' pool logs in as `postgres`, and `SET LOCAL ROLE authenticated` does not stop that session switching back: both SI-27 suites characterise that `RESET ROLE` returns to `postgres`. What keeps the channel out of `ops` is code and one privilege fact. The pool is private to `_shared/db.ts`, whose only use is `runAsUser`, and `merge_contacts` sends fixed statements through it. Both files are sealed by `tests/ownerSessionSeal.test.ts`: an independent review on 2026-09-13 showed that a static guard cannot read every spelling of a raw call (a computed member name, reflection), and found changes to these files that the guard alone accepted. SI-03 keeps every other function from importing the pool or another function's files. And `authenticated` holds nothing in `ops`. `tests/owner_session_pool.sql` proves the database side on one session. `tests/ownerSessionPool.mjs` runs `db.ts` through the real deno-postgres driver and Kysely in the local edge runtime, with one appended line that hands its probe the private pool, and proves that a committed merge, a thrown error, a missing contact and a database error each leave the one pooled session as the owner, with no role, identity, tenant context or open transaction, on the same backend. Not exercised: a COMMIT that itself fails, a connection that breaks mid-transaction, and a hosted pooler. Changing either sealed file is a review event the seal enforces: review the change against this invariant, run `npm run test:db`, then record the new digest.
- **SI-21 and SI-24 were restated for Phase 1D (2026-09-14).** SI-21 said every Company OS function is SECURITY INVOKER; Phase 1D adds six SECURITY DEFINER worker capabilities, lease-bound exactly like the Phase 1B capability, and every owner service stays INVOKER. SI-24 said no kind is task-executable; exactly `agent_run.execute` now is, and the bridge creates it only for a pending run of the same task. Both are proven against the real allowlist, not one replaced inside a rolled-back transaction.
- **SI-29 is at most once, not exactly once.** A run whose attempt died, or whose settle transaction failed after the provider answered, is `indeterminate` even when the call succeeded, or never left the process. A person decides whether to request a retry, which is a new run. No provider idempotency exists for the Responses API, so nothing below the database could deduplicate a second call; the database's durable start is the whole mechanism. **Owner review (2026-09-16):** a run is `failed` only when the provider was never called or its answer settles the outcome. Every 5xx, a timeout, a lost connection, and an unreadable or unfinished answer are `indeterminate`, in the adapter, in the database function and in the table's CHECK.
- **SI-30 has SI-14's bound.** A fully malicious worker process holding a legitimate lease can misreport its own run's outcome, usage or error category. It cannot reach another run, another tenant or any table. The claim hands the worker agent and task text, which it sends to the provider.
- **SI-31 states the agent-run part of the switch.** *(Restated 2026-09-17, Phase 1D.1.)* Holding every external job at the lease, the `job_kind` scope and the pre-call re-check for every handler are SI-37; the spend ceiling that trips the switch is SI-36. There is still no tool scope and no UI. A stop does not interrupt a call already started; that call is bounded by its route timeout and the lease deadline. The owner can still `DISABLE TRIGGER`, as for SI-22 and SI-23.
- **SI-32 is about what the system does with output, not what output says.** A summary or proposed step can carry prompt-injected text; nothing in Phase 1D acts on it, and any future reader that does inherits that risk. Task and agent text reaches the provider, whose abuse-monitoring retention applies despite `store: false`: only synthetic data may reach a live provider until BASELINE Q8 is decided.
- **SI-33 reads the build through source maps.** Vite replaces `import.meta.env.VITE_X` with its value, so without source maps a provider value that is not key-shaped could ship under a `VITE_` name with no finding. The older `assigned-server-secret` rule still misses prefixed and JSON-quoted forms of its existing names, and providers other than OpenAI and Anthropic are not named. Nothing inspects a worker's runtime environment.
- **SI-34 leaves one Phase 1C residual.** The Phase 1C owner services still accept a caller-declared `correlation_id` for their own lifecycle events (ADR 0016 §5); agent run facts never read it. An idempotency key is not a secret and grants nothing.
- **SI-35 is an estimate, not an invoice.** Cost is usage times a price an owner recorded; provider invoices remain the reconciliation source. The reservation assumes a byte-level tokenizer and that `max_output_tokens` bounds every generated token (true for the OpenAI Responses API, where it includes reasoning). The zero charge for a refusal relies on an adapter contract: an HTTP refusal carries no response id, no model and no usage, and `openaiResponses.test.ts` pins it for every non-2xx status. A price is keyed on the configured model id, so a route should name a pinned snapshot; `npm run ops -- runs` shows the requested and reported model side by side. The Phase 1C length checks trim only spaces, so an owner can store a title, name or role longer than its nominal limit; the start then reserves for the real text, and the operator's "largest reservation" is only the largest for text within the checks.
- **SI-36 fails closed on configuration.** With no global ceiling or no tenant budget, every run is refused and says why; a deployment must record a price and set both limits before its first run (`npm run ops -- price record`, `limit set`). Admission counts calls in flight at their reservation, so a burst can be refused by contention while settled spend is low: such a run retries on its job's backoff (`OS429`, transient) and its job fails after the last attempt (five by default); contention never trips the ceiling stop, which trips only on settled spend (settled spend reaching the ceiling, or a run refused because settled spend could not absorb its reservation). The global spend lock serialises every start fleet-wide. A start holds it only for the end of its transaction; a settlement whose charge rises and a global `limit set` or `limit retire` hold it for the rest of theirs. For a transaction opened through `createWorkerDatabase` (the worker and every `npm run` CLI), `idle_in_transaction_session_timeout` (10 s) bounds how long a stalled holder keeps it between statements, and the worker's `statement_timeout` (30 s by default) bounds a wait inside one. **Recorded residual (owner review 2026-09-17):** an owner session opened elsewhere (psql, Studio) has no idle bound. If it leaves a global limit change open, every start waiting behind it fails at its `statement_timeout` (57014, transient), each failure spends a job attempt, and after the last attempt the job fails and the run is recorded `failed` / `job_failed`. Make owner limit changes through `npm run ops`. Erasing today's runs frees today's budget: erasure is an owner act, and the owner can raise a ceiling anyway.
- **SI-37 holds, it does not cancel.** *(Restated 2026-09-17, owner decision B.)* A job held at the lease waits in the queue and runs once its stop is cleared; its run's start re-checks every gate then. A run whose job was leased before the trip is held at start too: the start answers `stopped` and writes nothing, and the runtime defers the job in the same transaction, under the kill-switch lock the start still holds (SI-31). Only a request made while a stop covers it is refused and recorded, before any job exists. A deferral whose stop was cleared between the generic pre-call check and the deferral fails that attempt through the transient path; the agent run path cannot meet that race. An unknown organisational coordinate fails closed inside its tenant, so a department or agent stop also holds a task-linked job of that company that no agent run describes. While an organisational stop is active, every lease reads each held job's coordinates; with only global, tenant or kind stops it does not.
- **SI-38 is opt-in per call.** A create without a key keeps the old, non-deduplicated behaviour; the future wrapper contract must require a key from every integration. Correlation is not part of either fingerprint, and the caller-declared `correlation_id` residual (SI-34) stays open.
- **SI-39 is an owner tool, not a boundary.** Whoever holds `ADMIN_DATABASE_URL` can do everything the owner can. What SI-39 guarantees is that the tool itself stays read-only by default, never needs a provider key, and prints no content. The routes it shows are what each of the 50 most recently seen workers, stopped and crashed ones included, published when it started; each row carries `lastSeenAt` and `stoppedAt`, so liveness is the operator's judgement.
- **SI-40 is proven by reading the workflows until GitHub runs them.** A job's `needs:` cannot reach a job in another workflow run, which is why `deploy.yml` runs the live-database job itself instead of waiting on `check.yml`'s: both call `.github/workflows/database.yml`, so there is one definition and the deploy is gated on the commit it ships. Each push to main therefore runs the suites twice, once per workflow. The guard reads line by line and refuses every spelling it would have to guess at; an adversarial review in Phase 1D.2 found seven bypasses in its first version, and each is now a test. Out of reach: a deploy through an npm or node script or a third-party action's code, a credential held in a configuration variable, a person running the makefile's deploy target, and branch protection, which is repository configuration. A red `database` job now blocks the hosted deploy, including for a failure unrelated to the change.
- **SI-41 closes the owner bootstrap deadlock without trusting the legacy flag.** From `20240730075029` until `20241104153231` any signed-in user could set their own `administrator` flag, so the upgrade does not promote on it: it halts, and a person chooses (PERMISSIONS.md §3). The halt happens after `20260911232039` has already applied, because the CLI commits each migration file on its own (measured); the bootstrap function is applied before the guard so that a halt always leaves a way forward. `bootstrap_owner` names the user by auth id, and an invited user must accept the invitation before it accepts them. The `users` edge function's half-state paths are recorded in the row's caveat and in SECURITY.md; they predate this phase and remain open.
- **SI-42 settles who may record an opt-out, not what the opt-out stops.** No code path yet refuses to contact a lead whose flag is set; the flag is stored, scoped and preserved. The backfill dates a legacy lead's acquisition from its earliest recorded evidence, not from the upgrade.

## Running the guards

```bash
npx vitest run --config vitest.config.ts   # static guards + unit tests, no Docker
npm run test:db                            # live-database suites; FAILS if no database is reachable
```

`npm run test:db` deliberately fails rather than skipping when it cannot connect. A security suite that did not run has verified nothing, and a skip reads as a pass in every CI summary.

## Adding an invariant

Add it to `supabase/tests/securityInvariants.test.ts` **first** — that file is the source of truth — then add the row here. Point it at a guard that actually runs. The test fails if an enforcement point is missing, if its assertion has been renamed away, or if this document and the code disagree.
