## 0. Summary of the approved architecture

1. **Frontend (OD-1, accepted):** an in-app, ra-core-free Company OS module at `src/company-os/`, built on the unmodified `src/components/ui/*`, with its own in-memory query cache, selected by a small top-level switch in `src/App.tsx`. `<CRM/>` is not edited and not wrapped in another router. No workspace, no `apps/ops-web`, no edits to `src/components/atomic-crm`, `admin` or `ui`. A separate Vite entry is a fallback only if spike S0.1 proves the in-app boundary impractical (§6).
2. **API (OD-2, accepted):** a narrow PostgREST RPC surface in a dedicated, **function-only** schema, `company_os_api`. It is not CRUD, not arbitrary SQL, not table exposure and not a generic `ops` proxy. Every RPC is designed and pinned individually. `ops` stays unexposed (§7).
3. **Privilege model (OD-8 owner amendment; OD-8a accepted with a strict pinned guard exception):** the browser reaches `ops` only through a pinned capability graph (§7.3):

   ```
   authenticated
     ↓ EXECUTE
   company_os_api RPC (owned by the NOLOGIN role ops_operator_api)
     ↓
   identity and membership gate (ops.gate_<op>, one per operation)
     ↓
   exactly one approved internal projection or act
     ↓
   ops
   ```

   `ops_operator_api` is NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOBYPASSRLS and NOINHERIT; it holds USAGE on `ops` and EXECUTE on exactly the gate set, and no table, column or sequence privilege beyond the catalogue reads PUBLIC gives every role, no CREATE, no generic write authority and no member through which the browser, PostgREST or an application login could `SET ROLE` into it (only a superuser or CREATEROLE role, the database-owner trust root, could grant itself membership). Function ownership is not the boundary; the exact callable graph is.
4. **Identity (OD-3, accepted; final confirmation):** an explicit Company OS human principal keyed to the stable Supabase Auth user id (the JWT `sub`, the value `auth.uid()` returns) and a tenant-generic membership (the ADR 0004 addendum), written only by a person holding the database-owner credential. **Same email ≠ same principal:** an email never selects or authorises a membership; the email at grant is kept only as a detection signal. In Phase 2C, memberships are provisioned and enabled only for the tenant that owns the local CRM; that is a temporary eligibility policy, not a data-model constraint (§7.4). The browser never chooses its tenant.
5. **Two browser mutations, and only two (OD-4, accepted):** decide an existing review (accept, reject, needs_edit) through `ops.record_review_decision`, and **trip** a stop at tenant, company, department or agent scope through `ops.trip_execution_stop`, with bounded lock contention. **Accepting sends nothing** (REVIEW ACCEPTANCE ≠ WHATSAPP SEND): a browser decision decides the structured triage review, never the hidden reply draft, authorises no send, and is never presented as a message approved for sending (§7.5). The browser never clears a stop (OD-6).
6. **Minimised projections (OD-5, OD-7):** tenant-scoped data only. No stored body or phone number, no reply draft, raw job error, provider secret or internal id, global sequence value or platform-wide identifier reaches the browser (the advice's model-written summary may echo a synthetic or test message). Platform state is one derived boolean, `globalAdmissionBlocked`, plus the pinned effects a platform stop can have on the tenant's own rows (§9). The structured review advice (for `lead_triage`, its classification enums, summary and recommended next action) appears only after an explicit open, only for synthetic or test origins, and never in durable browser storage; **the reply draft is never shown in the browser** (final confirmation, SI-52).
7. **Truthful state:** an agent is "working" only with a running AgentRun whose job holds a live lease, and every state carries the ids of the rows that prove it (§10).
8. **Mutations gated (OD-11; final confirmation):** read-only surfaces may be built first. The two browser mutations stay **disabled at the backend, not behind a frontend flag**: their functions exist in no database at rest (planning prototypes run only inside rolled-back transactions, §19) until the user-management prerequisite (the `users` edge function's `patchUser` authority and ordering, and the `createSale` half-state) is closed and tested (§19).
9. **Guards move with the surface:** the static migration guard (a new `company_os_api` branch, a new scrutinised role and the pinned OD-8a exception), live SQL pins, the Data API probe with real signed-in users, config pins, `scan:build`, ESLint and proposed invariants SI-54 to SI-59 land with the code they guard; SI-15, SI-21, SI-39 and SI-52 are amended by owner decision, approved in principle as narrow exceptions, with the final, owner-approved exact texts in §15 (SI-21 and SI-39 corrected at the owner's pre-push review).
10. **Sequence (decision P):** 2C operator surface, 2D decision engine and Jev, 2E observability and intelligence, then 3A, 3B, 3C. Jev is not added in 2C (§22, §23).

## 2. Goal

Let the owner **observe and narrowly steer** the existing Company OS through a real UI, over **real durable backend state only**.

> If the UI says something is happening, a durable backend fact supports it.

- An agent shown as working corresponds to a running AgentRun with a live job lease.
- A message status shown corresponds to a stored communication fact.
- A review shown corresponds to a `review_items` row.
- A cost shown comes from runtime governance data, computed in SQL.
- A stop shown as created corresponds to a committed `execution_stops` row; the UI never shows one before the database commits it.

**The frontend does not become the authority.** Backend and database governance stay authoritative. No fake activity, no simulated workers, no fake agent status, and no decorative state that a durable backend fact does not support.

## 3. Non-goals

Phase 2C does **not**:

- expose `ops` through PostgREST, or grant anything on `ops` to `anon`, `authenticated`, `service_role` or PUBLIC;
- move authority (permissions, budgets, the kill switch, consent, finality) into the browser;
- add a generic CRUD or SQL endpoint, a generic `ops` proxy, a generic function-name or JSON "operation" argument, or any query language over `ops`;
- send WhatsApp from the UI, merge acceptance with sending, show the reply draft in the browser, or add a resend, retry or mark-indeterminate path;
- create, activate or reconfigure any WhatsApp channel, or offer anything that could open the production gate;
- make a live Meta call, use real patient data, or send real content to any model;
- use an email as Company OS authority;
- enable Company OS membership for a tenant that does not own the local CRM (a temporary Phase 2C eligibility policy, §7.4);
- add Jev, a DecisionPort, a DecisionVector or any decision-engine code, dependency, environment variable, schema or migration (Phase 2D);
- add observability infrastructure (Phase 2E);
- add notifications of any kind: email, push or WhatsApp (OD-13, deferred);
- build an omnichannel inbox, a conversation client, a message list or a message composer (decision M);
- resolve the PUBLIC helper debt (ADR 0018 amendment 3), explicitly or implicitly;
- mutate the CRM, change organisational-unit status, or change security or governance configuration;
- build the isometric or game-like company view, or do visual polish beyond clean use of existing components;
- create a monorepo, a workspace or `apps/ops-web`;
- add a new npm dependency, a new always-on process, a new origin, a new login role or a new public generic API.

### 4.1 What exists and can be reused

**Authoritative `ops` services.** All are SECURITY INVOKER and executable only by the database owner, and all but `ops.spend_status()` take an explicit `p_tenant_id` (SI-21, `docs/SECURITY_INVARIANTS.md:50`):
- `ops.record_review_decision(p_tenant_id, p_review_id, p_decision, p_reviewer, p_source, p_note)` (`supabase/migrations/20260917190000_lead_triage_pilot.sql:649-724`):

### 4.2 What does not exist

- **No path from a browser, an edge function or a human role into `ops`.** Every operator act runs as `postgres` through `ADMIN_DATABASE_URL` (`engine/cli/cliOutput.ts:10-12,33`).
- **No human identity in `ops`:** no principal or membership table (ADR 0004 Proposed and deferred until an approver exists, `docs/adr/0004-principal-model.md:26-30`); `auth.uid()` appears in no `ops` migration; every actor is free text typed at the CLI.
- **No link from a CRM user to an `ops` tenant.** The only bridge is `ops.tenants.owns_local_crm`, a capability-authorisation flag at most one tenant may hold; the development seed leaves it false (`supabase/seed.sql:33`).
- **No production read** of `ops.events`, `ops.tasks`, `ops.agents`, `ops.companies`, `ops.departments`, `ops.conversations` or `ops.inbound_messages`.
- **No tenant-scoped cursor, no `(tenant_id, created_at)` index on `ops.events`, and no agent-state read model.**
- **No UI kill switch.** ADR 0010 2(c)'s UI half is recorded as "Not built" (`docs/adr/0010-cost-control-and-kill-switch.md:98,126`).
- **No worker API.** `docs/ARCHITECTURE.md:47-49,86` draws `Browser → ops-web → worker HTTP`, and the ROADMAP's Phase 7 scopes `apps/ops-web` on admin guessers; the worker serves no HTTP, and ADR 0018 argues against giving it one (`docs/adr/0018-whatsapp-transport-and-human-send.md:21`). ### 4.3 Facts that shape the design

1. **Lead-triage tasks never leave `assigned`.** Admission assigns them (`supabase/migrations/20260918150000_whatsapp_transport.sql:674-678`), and no production code calls `ops.transition_task`. Task lifecycle status is not a progress signal.
2. **`needs_edit` is a dead end.** One review per run, and only an accepted review can be sent.
3. **Stop trips, price records and spend limits write no `ops.events` row.** A global stop has no company, and `events.company_id` is NOT NULL.
4. **`events.created_at` is the transaction start;** `seq` orders events within a transaction (`20260912200000_company_domain_core.sql:322-325`).
5. **`ops.whatsapp_send_eligibility` is VOLATILE,** takes the kill-switch advisory lock in shared mode and reads `public.contacts` (`supabase/migrations/20260918170000_whatsapp_q8_gate_and_acknowledgement.sql:254-310`). It never backs a UI read.
6. **PostgreSQL grants EXECUTE on every new function to PUBLIC,** and a per-schema default revoke does not remove it (measured for `ops`, `docs/PERMISSIONS.md:193`).
7. **Privilege re-checking (measured, ADR 0015 §4, `docs/adr/0015-company-os-domain-core.md:38-39`):** table and schema privileges are re-checked on every execution; EXECUTE on an inner helper is re-checked per transaction when it is called with parameters, and folded into the cached plan for the life of the backend when it is called with constant or no arguments. **Schema USAGE and table privileges are therefore the robust runtime gates; an EXECUTE allowlist is a graph edge proven by catalogue pins, not a runtime boundary on its own.** SECURITY DEFINER SQL functions are never inlined, so a DEFINER body really runs as its owner.
8. **Function ownership on PostgreSQL 15** (`supabase/config.toml:25`): a non-superuser may change a function's owner only if it owns the function, is a direct or indirect member of the new owning role, and the new owner holds CREATE on the function's schema. Replacing or dropping a function, or changing its ACL, needs ownership (or membership in the owning role, with INHERIT). The repository's documentation says migrations run as `postgres`, which is not a superuser but has CREATEROLE, which on PostgreSQL 15 lets it grant membership in any non-superuser role; **the migration identity is not assumed here: implementation proves it (spike S0.4).** On PostgreSQL 16 and later a non-superuser `CREATE ROLE` gives its creator ADMIN membership automatically (so "no members at rest" would need that membership revoked) and the ownership check needs the SET option, which changes the pinned grammar: the mechanics here are PostgreSQL 15 facts, re-derived by the OD-12 readiness step for any hosted version. NOT MEASURED here (spike S0.4).
9. **The static guard cannot express that ownership change today.**
   - A top-level role-membership GRANT (`grant <role> to <role>`, no ON clause) is **unclassifiable and non-overridable** (`supabase/invariants/parse.mjs:468`; `supabase/invariants/overrides.mjs:26-28`, "Non-overridable by design"). A REVOKE passes unread: `parseGrant` returns null for it (`parse.mjs:462`) and no handler exists.
   - `ALTER FUNCTION` is not scrutinised (`supabase/invariants/sqlStatements.mjs:331`, `security: false`), nor are `alter sequence`, `alter type` or `create schema` (`:332-333,358`); no rule reads `OWNER TO`; `revoke` is not a DO-block hazard verb (`supabase/invariants/doBlocks.mjs:24-41`); `SET ROLE` is outside the SET model (`supabase/invariants/rules.mjs:604`). No migration uses `SET ROLE` or `SET SESSION AUTHORIZATION` today.
   - `overrides.mjs` accepts any ADR whose status starts with "Accepted" as an override authority once it names a migration file.
10. **The static guard does not see a new schema.** `isOpsObject` matches `ops` and `ops.` only (`parse.mjs:81-88`); EXECUTE and USAGE to `authenticated` are allowed privileges (`parse.mjs:91-98`); `enforcedSchemas` is a frozen `["public","ops"]` (`supabase/tests/migrationInvariants.test.ts:83,153`); there is no SECURITY DEFINER rule; A5 is a name allowlist of DEFINER functions in `ops` (`company_domain_core.sql:308-323`), and K3 fires only for functions `ops_gateway` can reach.
    - **Caught today, in any schema:** a GRANT to `anon` or PUBLIC, a GRANT to an undeclared role, and a write verb or schema-wide GRANT to `ops_worker` or `ops_gateway` (`rules.mjs:375-446`); a schema-wide grant to `authenticated`, and ALL, TRUNCATE, TRIGGER or REFERENCES to it (`rules.mjs:447-468`); `ALTER DEFAULT PRIVILEGES … GRANT` to `anon`, `authenticated` or PUBLIC (`rules.mjs:546-556`); a view outside `enforcedSchemas` (`view-foreign-schema`, `supabase/invariants/replay.mjs:212-224`).
    - **Unguarded until new guards land:** the implicit PUBLIC EXECUTE; a per-function EXECUTE or schema USAGE grant to `authenticated`, `ops_worker` or `ops_gateway`; any grant to `service_role` or another bypass role (exempt at `rules.mjs:374`); SECURITY DEFINER bodies; ALTER FUNCTION; and the schema's exposure.
11. **The Data API probe knows only the literal schema `ops`,** and has no signed-in `authenticated` user in its credential matrix (`supabase/tests/opsDataApiExposure.mjs:24-29,347-367`).
12. **ESLint flat config replaces a rule's options per block** (`eslint.config.js:10-15`); a new `no-restricted-imports` block that forgets the SI-19 persister ban silently drops it.
13. **Every Supabase Auth user is a CRM user.** `handle_new_user` gives every auth user an active `public.sales` row with role `operator` (`20260911232039_pending_delta.sql:601-619`), which can read the CRM's configuration and insert contacts, companies, deals, notes and tasks (`:784-790`, `:849-863`). Contacts feed `ops.crm_contact_by_phone`, the WhatsApp send-eligibility ContactPolicy of the tenant that owns the local CRM. Today the Auth directory and the CRM are coupled and single-tenant; the Company OS membership model must not inherit that coupling.
14. **A CRM administrator can change another user's auth email and lift a ban** through `patchUser` before its owner check (`supabase/functions/users/index.ts:205-213`); a password recovery then yields a live, unbanned session for the same auth user id. Fixing the ordering alone would still let the active CRM owner, who is also a CRM administrator (`isOwner`, `supabase/functions/users/index.ts:57-58`), change another user's auth email, so the OD-11 prerequisite (§19 S7) must close the authority issues as well as the ordering. Until it is merged and tested, this is a real account-takeover prerequisite debt (§14 item 2).

It never says "message approved", "approved for sending", "send approved" or an equivalent (§7.5, "What a browser review decision means")

A trip's contention or timeout answer renders "Stop request could not be completed yet. Retry." and nothing is shown as created.

### 7.2 Why A

### 7.3 The least-privilege capability graph (OD-8, owner amendment)

**The rule.** Function ownership is **not** the security boundary. The boundary is the exact callable capability graph. **Function owner** (which role's privileges a function body runs with) is distinct from **effective authority** (what a browser caller can actually cause), and the graph keeps the second minimal even where the first must be the table owner.

**Definitions used in this brief.** *Browser-reachable functions* are those `authenticated` or `ops_operator_api` can execute: the L3 and G functions. *Graph bodies* are the L3, G, resolver and L2 bodies. L1 bodies are the existing, unchanged services and are outside the graph-body rules.

**Layers:**

| Layer | Objects | Security mode and owner | EXECUTE held by | What it may do |
| --- | --- | --- | --- | --- |
| **L3 — exposed RPC** | `company_os_api.<op>`, one per catalogued operation | SECURITY DEFINER, `search_path = ''`, **owned by `ops_operator_api`** | `authenticated` only | Its body is exactly `select ops.gate_<op>(<same arguments>)`: no table, no column, no other function |
| **G — identity gate** | `ops.gate_<op>`, one per L3 function (1:1) | SECURITY DEFINER, `search_path = ''` (the trip gate, `ops.gate_trip_stop`, also carries a bounded `lock_timeout`), owned by the migration owner (the owner of the `ops` tables) | `ops_operator_api` only | First statement resolves the caller (`ops.operator_scope()`); then calls exactly one pinned L2 or L1 function, passing only the resolved tenant and actor plus the caller's selectors; sets `response.headers` with a constant through `pg_catalog.set_config`; maps errors |
| **Resolver and L2 — internals** | `ops.operator_scope()`; the eligibility predicate `ops.membership_tenant_eligible`; the projections `ops.read_*`, `ops.agent_operational_state`; the act helper `ops.trip_stop_in_tenant` | SECURITY INVOKER; they run as the owner inside a gate | nobody (owner only) | Read minimised projections with explicit column lists; `ops.membership_tenant_eligible` reads only `ops.tenants.owns_local_crm`; `ops.trip_stop_in_tenant` calls only `ops.trip_execution_stop` |
| **L1 — existing services** | `ops.record_review_decision`, `ops.trip_execution_stop`, the STABLE evaluators | unchanged (SECURITY INVOKER) | nobody (owner only) | Unchanged authoritative semantics |

**Roles:**
- **`authenticated`** (PostgREST, verified JWT): USAGE on `company_os_api` and EXECUTE on the L3 functions. Nothing on `ops` (A2 unchanged).
- **`ops_operator_api`** (new): **NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOBYPASSRLS, NOINHERIT**; no login role and no password (no process ever connects as it); owns exactly the catalogued L3 functions and nothing else; holds USAGE on `ops` and EXECUTE on exactly the G set. Measured with `has_function_privilege` (PUBLIC included), it executes exactly the G set in `ops` and, outside `ops`, `pg_catalog` and `information_schema`, in the schemas where it holds USAGE (the K5 scope), only the pinned K5 list measured in S0.4 (its own L3 functions, which an owner implicitly executes, plus whatever PUBLIC already executes there, the six PUBLIC CRM SECURITY DEFINER helpers included; the PUBLIC-derived entries are existing debt, not approved). It has no `has_table_privilege`, `has_any_column_privilege` or `has_sequence_privilege` on any relation in `ops` or in any other schema where it holds USAGE, outside `pg_catalog` and `information_schema`, whose catalogue relations PUBLIC lets every role read (the K1 and K2 shapes, `supabase/tests/whatsapp_transport.sql:742-766`), **no CREATE on any schema or on the database at rest (in particular none on `company_os_api`, `ops` or `public`)**, no generic write authority, no membership in any role, and **no members at rest**: not the migration identity, `authenticated`, `anon`, `authenticator`, `service_role`, `ops_worker` or `ops_gateway`, and no login role's membership closure contains it. So neither PostgREST (whose authenticator can switch only into roles it is a member of, whatever role a JWT claims) nor any login that is neither a superuser nor a CREATEROLE role can `SET ROLE` into it. A superuser, or a CREATEROLE role such as `postgres` (§4.3 item 8), could first grant itself membership; such a credential is the database-owner trust root (§14 item 3), and S0.4 measures and pins which roles hold it (M8).

**Why the gates are owner-owned, and why the role executes gates rather than projections.** The services and evaluators run on FORCE-RLS tables with lease-only policies, and the evaluators raise under active row security (`runtime_governance.sql:733-737`). A non-superuser `postgres` cannot create a BYPASSRLS role, and table grants to a new role would break SI-21 and A1 and would remove the `42501` backstop. So the identity check must run as the table owner before any projection, and the gates and their callees run as BYPASSRLS `postgres`. OD-8's "EXECUTE only on approved projections/services" is therefore realised as EXECUTE on **one gate per approved projection or service**; `ops_operator_api` holds no EXECUTE on any L2 or L1 function (pinned, §16). The role's `42501` backstop covers the exposed layer; a gate or projection defect still runs as the owner (§14 item 1).

**Why each gate holds at runtime** (ADR 0015 §4, §4.3 item 7):
- `authenticated` cannot reach any `ops` function: it lacks USAGE on `ops`, and schema privileges are re-checked on every execution.
- An L3 body cannot read an `ops` table even if it were written to: `ops_operator_api` has no table privilege, and table privileges are re-checked on every execution. A wrapper bug fails with `42501`, not with a leak.
- The only way from L3 into `ops` data is a G function, and no G function takes a tenant, company, actor, reviewer, source or causation **context** parameter (no parameter named `p_tenant%`, `p_company%`, `p_actor`, `p_reviewer`, `p_source` or `p_causation%`): it derives them itself from the verified claims and the membership, and every uuid argument is a pinned selector resolved inside that tenant (the company of a company-scope trip is `p_target_id`, checked against the caller's tenant, §16). Holding EXECUTE on G therefore confers no ability to name another tenant.
- The G → L2/L1 edges and the L3 → G edges are pinned by catalogue tests (`prosrc` shape, callee allowlist, ACLs), because an EXECUTE grant alone is not a runtime boundary.

**What the graph must prove (spike S0.4, then §16):**

```
authenticated
  ↓ EXECUTE
company_os_api RPC
  ↓
identity + membership resolution
  ↓
one approved internal projection or act
  ↓
ops
```

and **never**:

```
browser
  ↓
generic privileged reader
  ↓
arbitrary ops access
```

**Signatures.** Every browser-reachable function's full signature (argument names and types) is pinned. Every uuid argument is one of the selector names `p_agent_id`, `p_task_id`, `p_run_id`, `p_review_id`, `p_subject_id`, `p_target_id` (`p_subject_id` is resolved inside the tenant for its `p_subject_type`); the other arguments are the closed enums, cursors, limits and free-text fields listed in §8. No wrapper can choose a table, function, schema, SQL text, tenant, company, actor, reviewer or an action outside its own contract: there is no dynamic SQL, no function-name argument and no generic JSON "operation" argument. The tenant-taking L2 and L1 functions are executable by neither `authenticated` nor `ops_operator_api`.

**Other properties:**
- Every browser-reachable function returns one `jsonb` envelope, never `SETOF`, so PostgREST's `select=`, `order=`, `offset=` and counting cannot reshape it (`max_rows` 1000, `supabase/config.toml:16`).
- Reads are STABLE and acts VOLATILE, and every L2 read function and the resolver are STABLE too (STABLE constrains only a function's own statements); `ops.operator_scope()` is STABLE and **never IMMUTABLE** (an IMMUTABLE call with no arguments can be pre-evaluated at plan time and kept for the life of a pooled backend).
- Every G function sets `Cache-Control: no-store` on every successful response (PostgREST does not apply `response.headers` from a transaction that raises).
- Every G function raises one fixed, data-free message per operation and SQLSTATE (OS400, OS401, OS403, OS404, OS409, OS429, OS500); it never passes an L1 message, DETAIL or HINT through, and maps anything unexpected to OS500. Foreign equals missing therefore holds mechanically.
- **Bounded trip.** The trip gate (`ops.gate_trip_stop`) carries a function-level `lock_timeout`, fixed in S0.4 at a seconds-scale value and pinned; PostgREST's statement timeout for `authenticated` is the outer bound (NOT MEASURED, M4). A trip whose lock wait exceeds that `lock_timeout` (`lock_not_available`) is caught by name in `ops.gate_trip_stop` and answered with one fixed, data-free, retryable refusal (OS429), identical whoever holds the lock; nothing is created, because the transaction rolls back. A statement cancel, which PL/pgSQL `when others` does not catch, surfaces as PostgREST's own generic error and also creates nothing. The review-decision gate sets no `lock_timeout`, raises no OS429 and keeps `ops.record_review_decision`'s existing semantics; the statement timeout alone bounds its row-lock wait (NOT MEASURED, M4). Whether `lock_timeout` bounds the advisory-lock wait inside `trip_execution_stop` is NOT MEASURED (spike S0.4, M11); if the bound cannot be shown, the phase stops for owner review.
- Free-text inputs (the stop reason, the review note) refuse Unicode Cc and Cf characters with a data-free OS400, because they reach owner CLI output.
- Graph bodies schema-qualify every relation, type and function (`search_path = ''` still searches `pg_temp` first for relation and type names). No overloads; no dynamic SQL.

**ACLs:** every new function is revoked from PUBLIC, `anon`, `authenticated`, `service_role`, `ops_worker` and `ops_gateway` first; then L3 gets `grant execute … to authenticated` and G gets `grant execute … to ops_operator_api`; `grant usage on schema company_os_api to authenticated` and `grant usage on schema ops to ops_operator_api` are the only standing schema grants. An end-state `DO` assertion in the migration checks every ACL, owner, role attribute and role membership, in the style of `20260918150000_whatsapp_transport.sql:1283-1300`.

**Transport:** the browser calls `client.schema('company_os_api').rpc(name, args)` (POST). `company_os_api` is appended **after** the existing entries of `[api] schemas` (`supabase/config.toml:11` and `supabase/config.e2e.toml`, plus the gitignored copy `.supabase-e2e/supabase/config.toml`) and is **not** added to `extra_search_path` (`:13`). SI-15's marker pins the exact `schemas` literal (`supabase/tests/securityInvariants.test.ts:497`) and changes with the SI-15 amendment. Whether pg_graphql reflects a schema that is exposed but not on the search path is NOT MEASURED (spike S0.4, M1).

### 7.4 Identity, membership and tenant derivation (OD-3: accepted; final confirmation)

**The principal is the auth user id.** The authoritative human identity is the stable Supabase Auth user id: the verified JWT `sub`, the value `auth.uid()` returns. A membership binds **tenant + auth user id (through the principal) + membership state and role**. An email never selects, identifies or authorises a principal or a membership: **same email ≠ same principal.** Changing an email never transfers a membership, and a new auth user created with a former member's email holds nothing.

**Tables (the ADR 0004 addendum):**
- `ops.principals`: `id`, `kind` (check `human|agent|service`; only `human` is written in 2C), `issuer` (in 2C always the fixed label `supabase_auth`), `subject` (the auth user id), `display_name` (an owner-typed label of 1 to 200 characters that may not contain `@`, so no membership command can print an email-shaped label and SI-39's no-email clause holds mechanically), `created_by`, `created_at`, `disabled_at`, `disabled_by`; unique `(issuer, subject)` and unique `(id, kind)`.
- `ops.tenant_memberships`: `id`, `principal_id`, `principal_kind` (check `principal_kind = 'human'`, with a composite foreign key `(principal_id, principal_kind)` to `ops.principals (id, kind)`, so no agent or service principal can ever hold a membership), `tenant_id` (any tenant: the table carries **no** check, foreign key, trigger or column that ties a membership to CRM ownership), `role` (check `tenant_operator`; deliberately not `operator`, which the CRM's `sales.role` uses), `email_at_grant_sha256` (the SHA-256 of the auth user's lower-cased email at grant time: a detection signal, never authority), `granted_by`, `grant_reason`, `granted_at`, `revoked_by`, `revoke_reason`, `revoked_at`; revocation happens once and rows are never deleted; a partial unique index `(principal_id) where revoked_at is null` means one active tenant per person in 2C. That index is a Phase 2C limit, not a property of the tenant-generic model: letting one principal hold active memberships in several tenants later needs an owner decision, a forward migration that drops the index (no data migration) and a way for the resolver to choose among the caller's own memberships that never trusts a browser-supplied tenant.
- Both have ENABLE + FORCE RLS, no policy and no grant.
- **The binding is immutable** (ENABLE ALWAYS guards, in the style of `ops.communication_channels` and `ops.execution_stops`): they refuse an UPDATE of a principal's `id`, `kind`, `issuer`, `subject`, `created_by` or `created_at`; any UPDATE of a membership other than setting `revoked_by`, `revoke_reason` and `revoked_at` once, from null; and any DELETE or TRUNCATE of either table. A membership, and any recorded `principal:<uuid>`, therefore never points to another auth subject or tenant; a change of person or tenant is a revoke plus a new grant.

**The email at grant is detection only.** Only the owner CLI reads it: `npm run ops -- membership list` compares it with the auth user's current email and flags `emailChangedSinceGrant`, a tamper or change alarm during the temporary coupling of Company OS identity to the CRM's Auth directory. The browser path never reads an email: the resolver neither selects nor refuses by email, and no security property is claimed from a match (a recovery followed by restoring the original email would match anyway). The real control is the user-management prerequisite (§14 item 2, §19 S7).

**Provisioning:** only by `npm run ops -- membership grant|revoke` (new; `membership list` reads), through owner-only INVOKER services `ops.grant_membership` and `ops.revoke_membership`. `membership list` prints ids, the tenant, the role, the state and its timestamps, the `@`-free display name and `emailChangedSinceGrant`, and no grant or revoke reason, so SI-39's no-email clause holds mechanically.
- `ops.grant_membership` takes the auth user id (`--auth-user-id`), never an email; validates the auth user against `auth.users` only (confirmed, not banned, not deleted: the three `auth.users` conditions of `bootstrap_owner`, without its `public.sales` lookup) and reads no CRM table; records the email hash; refuses `system:` and `principal:` actor labels; and applies the Phase 2C eligibility policy below.
- The owner CLI validators for the three actor-label paths (`engine/domain/executionStops.ts`, `reviewQueue.ts`, `outboundMessages.ts`) refuse a typed `principal:` label in TypeScript, so an owner-CLI-written label can never be mistaken for a gate-resolved caller in the CLI's own output or when the authority relied on is reconstructed. No browser projection returns any of these labels (§9). The SQL still accepts any well-formed label from the owner credential (SI-39), so a `principal:` actor or `company-os-ui` source identifies a gate-resolved caller only on application paths.
- **No Phase 2C CLI act disables a principal:** `membership revoke` is the Company OS off-switch, and a principal act would need a reviewed extension of SI-39's act allowlist (§15).
- **Company OS authority keeps today's trust root, the database-owner credential.** The CRM's owner or administrator state never *derives* Company OS authority: the `users` edge function can make a CRM owner, never a Company OS operator. It can *capture* an existing member's login until the prerequisite is fixed (§14 item 2).

**Phase 2C eligibility policy (temporary, not core architecture).** In Phase 2C a membership is provisioned and enabled only for the tenant that owns the local CRM (`ops.tenants.owns_local_crm`). One eligibility predicate applies it: the owner-only, STABLE, SECURITY INVOKER function `ops.membership_tenant_eligible(p_tenant_id uuid)` (`search_path = ''`; revoked from PUBLIC, every application role and the capability role `ops_operator_api`). `ops.grant_membership` and `ops.operator_scope()` both call it, and no other function the Phase 2C migrations create reads `owns_local_crm`, which gains this consumer with no change to its existing meaning. The reason is the coupling in §4.3 item 13: every Company OS member is also an active CRM user of that tenant, so a member of any other tenant would gain the clinic's CRM and write access to contacts that feed its WhatsApp ContactPolicy. **The membership model itself stays tenant-generic:** lifting the policy changes one predicate, needs no data migration, and needs an owner decision that also separates that tenant's Company OS identity from the clinic's CRM trust model (CRM-side separation, a separate Supabase project, or another identity domain), so a future non-CRM or independently isolated business uses the Company OS without sharing the clinic's CRM. Another identity domain is more than that predicate change: the Phase 2C resolver and `ops.grant_membership` trust only the fixed `supabase_auth` label, do not compare the JWT `iss`, and check the local `auth.sessions` and `auth.users`, so that option first needs the resolver to bind the verified `iss` to `ops.principals.issuer` and to check that domain's own session and ban state; it needs no data migration, because `issuer` already exists.

**The resolver, `ops.operator_scope()`** (called as the first statement of every G function):
1. reads `current_setting('request.jwt.claims', true)::jsonb`, the JSON PostgREST sets after verifying the JWT; its `sub` is the auth user id, the same value `auth.uid()` returns for a PostgREST request, read directly because `auth.uid()` prefers the legacy per-claim setting `request.jwt.claim.sub` and only then falls back to the claims JSON (Supabase's definition, confirmed in S0.2, M2). The sealed `merge_contacts` pool sets only the legacy `request.jwt.claim.sub` (`supabase/functions/_shared/db.ts:209-213`), so it fails closed here; that is a second layer, not the containment, which still rests on the seal (SI-27);
2. requires `role = 'authenticated'`, `aud = 'authenticated'`, `is_anonymous` not true and a uuid `sub`, otherwise OS401; the JWT `iss` is not compared in 2C (the binding is PostgREST's signature check plus steps 3 and 4);
3. requires a live session: an `auth.sessions` row with `id = claims.session_id`, `user_id = sub`, and `not_after` null or in the future, so a sign-out or revocation takes effect on the next call rather than after `jwt_expiry` = 3600 s (`supabase/config.toml:98`). Readability of `auth.sessions` by the migration owner is NOT MEASURED (spike S0.2);
4. requires the `auth.users` row for `sub` to exist with `deleted_at` null and `banned_until` null or past; the CRM's "disable" bans the auth user (`supabase/functions/users/index.ts:213`), so no `public.sales` read and no PUBLIC CRM helper is needed;
5. requires an enabled `human` principal whose `(issuer, subject)` is `('supabase_auth', sub)`, with exactly one active membership; none raises OS403, more than one raises OS409;
6. requires the membership's tenant to satisfy the Phase 2C eligibility policy, otherwise OS403;
7. returns `(principal_id, tenant_id, role, actor)`, with `actor = 'principal:' || principal_id`, which matches both actor formats (`^[a-z0-9][a-z0-9_.:@-]{0,127}$`, `20260914120000_agent_runtime.sql:244`; the reviewer format above) and can never start with `system:`.

**Tenant derivation.** The tenant comes **only** from the membership. Every id the browser sends (review, run, task, agent, subject, stop target, cursor) is a selector resolved `where id = $1 and tenant_id = v_tenant`; a foreign id is answered exactly like a missing one; the existing services check the tenant again. A reference to another row that a projection emits is classified before it leaves: `{ id }` only when the row's `tenant_id` equals the caller's tenant, `null` when the row is platform-scoped (`tenant_id` null), and OS500 otherwise.

**Source provenance for UI acts:** `company-os-ui`, which `record_review_decision` accepts and which distinguishes UI acts from `operator-cli` in `ops.events`.

**Authority relied on.** The act rows store the actor label and the source, not the membership id. The authority relied on is reconstructed from `principal:<uuid>` and the membership's grant and revoke history.

**What a browser review decision means (owner's pre-push review, 2026-09-22; final).** The reply draft stays out of the Phase 2C browser, and the owner accepts that exclusion. The semantics are therefore explicit:
- A browser decision (accept, reject or needs_edit) is a decision on the **structured triage review**: the review item and, where shown, its structured advice (the classification enums, summary and recommended next action, shown only on explicit open and possibly withheld, §13). It does **not** approve the exact outgoing WhatsApp message, nor the hidden reply draft, which the member never sees.
- It does **not** authorise a WhatsApp send. An accepted review is one precondition that a later `npm run messaging -- send` requires when the send is requested (`ops.request_outbound_send`), alongside the SI-49 eligibility rule, which it checks at the request and again immediately before the call (ADR 0018 §4); that send stays a separate, deliberate operator act. REVIEW ACCEPTANCE ≠ SEND (SI-45; SI-58).
- No label, confirmation, status or fixed error text of the Company OS surface, and no audit row or event the act writes, describes a browser acceptance as a message, draft or reply approved for sending ("message approved", "message approved for sending", "approved for sending", "draft approved", "send approved" or an equivalent), unless a future explicit design creates that concept. The act records exactly the existing semantics: the review row's decision, `reviewer = principal:<uuid>`, source `company-os-ui`, and the existing `lead_triage.reviewed` event carrying the decision, unchanged. The service's own OS403 wording about a draft never reaches the browser: the gate raises only its fixed texts (§7.3).
- A send operator who needs to read the actual draft does so through the existing owner CLI path (`npm run ops -- triage show`), unless a future explicit owner decision creates another safe surface. Phase 2C does not expose the draft to solve this.
- Still recorded, not decided: nothing enforces that the send operator reads the draft before a send (§14 item 11).

### 7.6 The PostgreSQL constraint behind OD-8, and OD-8a (accepted with a strict pinned guard exception)

Making `ops_operator_api` own the L3 functions requires, at migration time (PostgreSQL 15, §4.3 item 8):
- the **migration identity** (the role that runs migrations, proven during implementation, not assumed) to be a **member** of `ops_operator_api` while it runs `ALTER FUNCTION … OWNER TO ops_operator_api`, and while it replaces, drops or changes the ACL of such a function later (which only a new migration with its own exact allowlist entry may do, A); and
- `ops_operator_api` to hold **CREATE** on `company_os_api` at the moment of each ownership transfer.

Today's static guard refuses the membership statement as unclassifiable and non-overridable, would flag the CREATE grant under the new `company_os_api` branch, and does not scrutinise `ALTER FUNCTION … OWNER TO` at all (§4.3 item 9). **OD-8a — ACCEPTED by the owner on 2026-09-22 as a strict, pinned guard exception** — extends the guard as follows. It is a pinned exception, never a broad one: nothing like "role grants are now allowed" is introduced.

**A. The pinned scope: exactly pinned, self-contained migrations, and no standing exception** (tightened at the owner's pre-push review, 2026-09-22, which settled the reading the earlier text flagged). One role (`ops_operator_api`), one schema (`company_os_api`), the exact Phase 2C RPC catalogue (every function name and signature, in `declaration.json`, pinned as a literal in `migrationInvariants.test.ts`), and an allowlist of exact migration files, each pinned in the static guard by its full file name (version and name): the S2 read-only migration and the S8 acts migration. Phase 2C needs two only because OD-11 makes the acts arrive later, and the pair is acceptable only because **each** migration independently carries the whole lifecycle below; neither relies on the other's window, and neither leaves anything for a later migration to clean up.

**Every allowlisted migration, in order:**
1. asserts that it runs as the proven migration identity (`current_user` and `session_user` equal the pinned literal, B) and raises otherwise;
2. `grant ops_operator_api to <migration identity>` (B);
3. `grant create on schema company_os_api to ops_operator_api`, only if its transfers need it (C);
4. only the exact catalogued ownership operations pinned for that file: for S2 and S8, the `ALTER FUNCTION … OWNER TO ops_operator_api` of the catalogued functions that migration itself creates, each function's ACL (no PUBLIC EXECUTE, EXECUTE to `authenticated`) being set before its transfer, while the migration identity still owns it (D; that the ACL survives the transfer is confirmed in S0.4, M9);
5. `revoke create on schema company_os_api from ops_operator_api` (C);
6. `revoke ops_operator_api from <migration identity>` (B);
7. the end-state assertion and then the suite's post-migration privilege proof (E).

**No standing exception.** OD-8a attaches to those exact files, not to the role, the schema or later work. S2 and S8 themselves replace, drop or change the ACL of no function the role already owns. There is **no** generic future exemption for `ALTER FUNCTION … OWNER TO`, `CREATE OR REPLACE FUNCTION`, `DROP FUNCTION`, GRANT or REVOKE of EXECUTE, `ALTER DEFAULT PRIVILEGES`, any other change to a function's ACL, or role membership: outside the allowlisted files, each of these on a `company_os_api` function, and every role-membership statement, is a non-overridable finding, and any `ALTER DEFAULT PRIVILEGES` that touches the Phase 2C privilege graph is a non-overridable finding in every migration, allowlisted ones included: any form (GRANT or REVOKE, with or without `IN SCHEMA` or `FOR ROLE`) that names `company_os_api` or `ops_operator_api`, and any GRANT form with no `IN SCHEMA` clause (which reaches every schema, `company_os_api` and `ops` included) or with `ops` in its `IN SCHEMA` list. No default privilege may give `ops_operator_api`, `authenticated`, `anon` or PUBLIC future authority over `company_os_api` or `ops` beyond the exact reviewed catalogue, so no generic or default future EXECUTE path exists (§15); only an explicitly reviewed future architecture change, through a guard update, can change that. A REVOKE form can only tighten (`supabase/invariants/rules.mjs:489`), and it is caught too because `company_os_api` carries no default-privilege statement at all: §15 forbids any relation, sequence, type or domain there, and every catalogued function's ACL is set explicitly in its own migration (A, step 4), so the deny-by-default revoke that `ops` needed has no counterpart here and any such statement is unreviewed drift. A later change to the catalogue or the privilege graph (a new, replaced or dropped operation, a changed ACL or gate grant, a rollback) needs a **new forward migration**, which, where it needs the membership, gets its own exact allowlist entry and runs the full lifecycle above; an **explicit static-guard update** (the pinned catalogue, gate and migration literals, never a `SECURITY-INVARIANT-OVERRIDE`); **reviewed tests**, red first; and **owner or governance review** wherever a capability changes.

**B. Temporary role membership.** Only inside an allowlisted migration, as its lifecycle steps 2 and 6 (A):
- the grant targets exactly `ops_operator_api`;
- the grantee is exactly the repository's proven migration identity. Its name is not assumed: spike S0.4 measures `current_user` and `session_user` on the local paths (a `db reset` of the e2e stack and the upgrade replay) and records what the CI workflow runs; the guard pins that exact literal; and each allowlisted migration first asserts that `current_user` and `session_user` equal the pinned literal and raises otherwise, so every apply (local, CI, the upgrade replay and any later hosted apply under OD-12) proves the identity rather than relying on the spike alone. The repository's documentation says `postgres`, which is not taken as proof;
- no `WITH ADMIN`, `SET` or `INHERIT` option and no `GRANTED BY`;
- a matching `revoke ops_operator_api from <migration identity>` occurs in the **same** migration, after the last statement that needs the membership; each migration applies in one transaction, so a failed migration also rolls the membership back (confirmed in S0.4, M9);
- **every other role-to-role grant involving the scrutinised Company OS roles (`ops_worker`, `ops_gateway`, `ops_operator_api`), and indeed every other role-membership GRANT, stays unclassifiable and non-overridable exactly as today** (`parse.mjs:468`, `overrides.mjs`), including the reverse direction, any grant of `ops_operator_api` to any other grantee, any grant of any role to `ops_operator_api`, and `current_user` or `session_user` as the grantee; every other role-membership REVOKE (unread today) becomes a non-overridable finding. A REVOKE parser is added for the two pinned pairs (membership and CREATE).

**C. Temporary CREATE on `company_os_api`.** Only inside the membership window of an allowlisted migration, bracketing the ownership transfers (lifecycle steps 3 and 5, A): exactly `grant create on schema company_os_api to ops_operator_api`, and the matching `revoke create on schema company_os_api from ops_operator_api` in the same migration after the ownership operations. **CREATE on `ops`, on `public` or on any other schema to this role, and any CREATE on `company_os_api` to it other than that pinned pair, is a non-overridable finding.** Nothing is left behind: after deployment the role holds CREATE on no schema and not on the database (PUBLIC's default TEMPORARY on the database is moot, because nobody can open a session as the role).

**D. ALTER FUNCTION … OWNER TO.** Arbitrary function ownership change becomes forbidden (today `ALTER FUNCTION` is not scrutinised, §4.3 item 9). An ownership transfer is allowed only when **all** of these hold: the destination owner is `ops_operator_api`; the function's schema is `company_os_api`; its name and signature are in the exact Phase 2C RPC catalogue; the statement is one of the transfers pinned for that allowlisted migration file (A, step 4); that migration contains both revoke pairs (B and C); and the post-migration tests (E) verify the final privilege graph. Every other `ALTER FUNCTION|ROUTINE|PROCEDURE … OWNER TO` is a non-overridable finding, whatever the destination (no migration uses `OWNER TO` today); the catalogue grows only by changing its pinned literal, never through a `SECURITY-INVARIANT-OVERRIDE`. Every other ownership path naming `ops_operator_api` (`CREATE SCHEMA … AUTHORIZATION`, `ALTER TABLE|VIEW|SEQUENCE|TYPE|DOMAIN|SCHEMA … OWNER TO`, `REASSIGN OWNED`), any `ALTER ROLE ops_operator_api`, and any `SET ROLE`, `RESET ROLE` or `SET SESSION AUTHORIZATION` (no migration uses them today) is a non-overridable finding. **Every rule in B, C and D applies at top level, inside a DO body and inside a resolved `EXECUTE` string;** an owner or role the guard can read only as a dynamic placeholder counts as naming `ops_operator_api`. Today a DO body is read only for the hazard verbs of `doBlocks.mjs:24-41`, and a top-level `alter function|sequence|type` or `create schema` is `security: false`, so these verbs join the DO-body hazard verbs and those heads become security-relevant. A `CREATE ROLE` or `DROP ROLE` naming `ops_operator_api` outside an allowlisted migration, and a creating statement that does not carry exactly NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS NOINHERIT, are also non-overridable findings, and `create function` becomes security-relevant for `company_os_api` (it is `security: false` today, `sqlStatements.mjs:348-350`) so the §15 branch reads every body. Only with that coverage can no object other than a catalogued `company_os_api` function come to be owned by the role; the end-state proof (E) re-checks it live.

**E. Post-migration proof** (the migration's end-state `DO` assertion, then the SQL suite): the role's attributes (NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOBYPASSRLS, NOINHERIT); the migration identity is no longer a member; `authenticated`, `anon`, `authenticator`, `service_role`, `ops_worker` and `ops_gateway` are not members; no login role's membership closure contains the role; the role is a member of nothing; it has USAGE on `ops` and no CREATE on `company_os_api`, `ops`, `public`, any other schema or the database; it owns exactly the catalogued L3 functions; it executes exactly the G set in `ops` and the pinned K5 list outside `ops`, `pg_catalog` and `information_schema` in the schemas where it holds USAGE; it holds no table, column or sequence privilege outside the catalogue reads PUBLIC gives every role (the K2 shape); the migration asserted that it ran as the pinned migration identity; the `pg_default_acl` entries reaching `ops` or `company_os_api` equal the S0.4 list and grant the role nothing; and the roles with `rolsuper` or `rolcreaterole`, and the login roles whose membership closure contains one, equal a list measured in S0.4.

**F. Residual privilege after migration.** `ops_operator_api` keeps only: ownership of the catalogued L3 functions (with the implicit EXECUTE an owner has); USAGE on `ops`; EXECUTE on the G set; and what PUBLIC grants every role (USAGE on `public`, the catalogue reads and built-ins, and EXECUTE on every function PUBLIC already executes, the six PUBLIC CRM SECURITY DEFINER helpers included; measured in S0.4, pinned by K5 and the K2 shape, recorded as existing debt, not approved, and not changed by Phase 2C). No application or runtime identity can exercise that ownership, because the role has no login and no members; only a superuser or CREATEROLE role (the database-owner trust root, §14 item 3) could, by first granting itself membership, and in a migration only the pinned OD-8a pair permits that.

This is not a weakening: today those statements are either refused outright or invisible, and the extension makes exactly two literal pairs and one catalogue-bound ownership transfer classified and pinned, per exactly named migration file, while everything else keeps today's refusal or becomes a new non-overridable finding. Every rule is red-tested first. **ADR 0019 authorises no `SECURITY-INVARIANT-OVERRIDE`:** its only guard change is OD-8a, and any override citing it needs a separate owner decision.

**If the pinned exception proves unworkable** (for example, if the proven migration identity cannot hold the membership), the narrowest equivalent capability model is to expose the G functions themselves in `company_os_api`, owned by the migration owner, with the graph pinned only by catalogue tests, which loses the mechanical `42501` backstop. It is **not** adopted; it needs a separate, explicit owner decision recorded in ADR 0019.

## 9. UI projections (contracts)

Each is a zod `.strict()` schema in `contracts/company-os-api/`, mirrored by the jsonb the L2 function builds. Status enums equal the engine vocabularies already pinned to SQL (`AGENT_RUN_STATUSES`, `REVIEW_STATUSES`, `OUTBOUND_STATUSES`, the task statuses), proven by a unit test. Money is bigint micros serialised as a **string**, plus a USD string formatted in SQL.

**Platform-derived state (OD-7).** Tenant operators receive tenant-scoped data only. The complete, pinned platform-derived set is:
1. **One derived boolean,** `platform.globalAdmissionBlocked` (in OverviewSummary and SpendSummary): true when a platform stop (a `global` stop, or a `job_kind` stop on `agent_run.execute` with no tenant) covers new agent runs, or the global spend admission is `blocked`;
2. **The effects a platform stop or the global ceiling can have on the tenant's own rows,** which carry no platform id, amount, count, reason, actor or time: `AgentSummary.activity` (queued → held) with `evidence.heldRunIds` and `evidence.queuedRunIds`; the OverviewSummary counts `agents.held`, `agents.queued`, `runs.todayByStatus` and `outbound.todayByStatus`; the tenant's own runs' `status`, `errorCategory` and `errorCode`; AgentRunDetail's `job.status`, `job.availableAt` and `jobSteps` (`job_deferred`); for a send blocked under a platform stop, `OutboundSummary.status` and `blockedReason`, `TaskSummary.pipeline.outbound.status` and `ReviewSummary.outboundStatus`; and, in the optional view, `outbound.byStatus` and `outbound.blockedByReason`.

Every reference to a platform-scoped row (`evidence.stop`, `stopRef`, `spendLimitRef`, `coveringStop`) is **null**; availability is `stopped` only for a stop naming the tenant. No platform amount, count, reason, actor, timestamp or identifier is returned, and a new platform-derived field needs an explicit owner decision. (The brief's first draft had a second boolean, `workerSeenRecently`; it is dropped, because the owner's allowance named only admission.)

- **OperatorContext:** `{ principal { id }, tenant { id, name }, role, dataPolicy: 'synthetic_or_test_only', allowedActions { decideReview, tripStop, viewAdvice }, serverTime }`. `dataPolicy` states the policy in force; it is not a proof about content (§14 item 12). `allowedActions` reports false for both acts while their functions do not exist. No display name: the principal's owner-typed `display_name` stays in the owner CLI (the actor-label rule below).
- **OverviewSummary:** `agents { total, working, held, queued, stopped, inactive, stale }`; `runs { todayByStatus, workingNow, needingAttention }`; `reviews { pending, oldestPendingAt }`; `stops { tenantScopedActive }`; `admission { tenantAdmission }` (from the tenant and company limit rows); `outbound { todayByStatus, indeterminateOpen, acceptedWithoutSend }` (counts; `acceptedWithoutSend` counts accepted reviews with no send recorded and is never labelled as awaiting a send, §7.5); `platform { globalAdmissionBlocked }`.
- **AgentSummary:** `id, slug, name, company { id, name }, department { id, name }`; `availability: inactive | stopped | available`; `activity: working | stale | held | queued | idle`; `attentionCount`, `lastRunAt`; `evidence { workingRunIds[], heldRunIds[], queuedRunIds[], staleRunIds[], attentionRunIds[], stop, inactiveUnit }` (arrays at most 20). `stop` is `{ id, scope, origin }` for a stop naming the tenant, otherwise null.
- **TaskSummary:** `id, type, lifecycleStatus, priority, dueAt, createdAt, company, department, assignedAgent { id, name }`, and `pipeline { latestRun { id, status } | null, review { id, status } | null, outbound { id, status } | null }`. Never `title` or `description`.
- **TaskDetail:** TaskSummary plus `runs`, `review`, `outbound` (an OutboundSummary or null), `inbound { sourceKind, channelLabel, receivedAt, contactResolution, doNotContact } | null`, and the first page of the task's `events`.
- **OutboundSummary** (inside TaskDetail only): `{ id, status, reviewItemId, taskId, channelId, blockedReason, errorClass, errorCode, authorizedAt, sendingAt, settledAt, deliveredAt, readAt }`. No recipient, body, draft or `requested_by` label.
- **AgentRunSummary:** from the CLI's `RUN_COLUMNS` (`engine/domain/runtimeReadModelRuns.ts:82-93`) without `tenantId` and without `priceId`: `id, companyId, taskId, agentId, retryOfRunId, capability, modelRoute, status, errorCategory, errorCode, provider, model, responseModel`, the five token counts, `latencyMs, jobAttempt`, the reserved, estimated and charged cost (micros strings and USD strings), `createdAt, startedAt, completedAt`, `attention: indeterminate_not_retried | running_without_live_lease | null`, `stopRef` (`{ id }` for a stop naming the tenant, otherwise null) and `spendLimitRef` (`{ id, scope }` for a tenant or company limit, otherwise null).
- **AgentRunDetail:** AgentRunSummary plus `retriedByRunIds[]`, `job { status, attempts, availableAt, leaseLive, lastErrorClass }`, `jobSteps: [{ step: job_leased | job_deferred | job_retry | job_reaped, attempt, at }]` (§11) and `coveringStop` (as `AgentSummary.evidence.stop`).
- **ReviewSummary:** `id, taskId, agentRunId, capability, status, doNotContact, reviewedAt, createdAt, hasNote, outboundStatus`. No reviewer label: the stored `reviewer` is free-form (the actor-label rule below). It carries no field of the model's proposal: the classification enums (`outcome`, `intent`, `priority`, `needsHumanReview`, `flags[]`; closed sets, `20260917190000_lead_triage_pilot.sql:128-193`), including content-derived flags such as `possible_crisis` and `minor`, are part of the structured advice and appear only in ReviewAdvice, on explicit open, for synthetic or test origins (final confirmation; the SI-52 amendment).
- **ReviewDetail:** ReviewSummary plus `decisionNote` and server-computed `allowedDecisions[]` (empty unless pending; `rejected` and `needs_edit` only for a do-not-contact item).
- **ReviewAdvice (OD-5; SI-52 amendment):** a **capability-pinned** projection, not a generic content viewer. In 2C only `lead_triage` has one: `{ reviewId, capability: 'lead_triage', outcome, intent, priority, needsHumanReview, flags[], summary, recommendedNextAction }`. **It never includes the reply draft** (`response_draft`, the text a CLI send would transmit, `20260918150000_whatsapp_transport.sql:1141-1146`), the stored inbound body or any task description, the sender's stored number, a secret, a token or a raw provider error. `summary` and `recommendedNextAction` are written by the model from the inbound message and may echo its words, including a number typed in it, which is why the read is limited to synthetic or test origins. Any other capability, a non-synthetic or non-test origin, or a proposal that fails the capability's output contract answers `{ reviewId, withheld: capability_not_pinned | origin_not_synthetic_or_test | contract_invalid }`.
- **EventSummary:** `{ id, type, source, subjectType, subjectId, causationId, createdAt, facts }`; `source` is a pinned provenance value or `other` (the actor-label rule below); `facts` holds only the payload keys allowlisted for that type; an unknown type gets `{}` and `factsWithheld: true`.
- **ExecutionStopSummary:** stops naming the tenant only: `{ id, scope, jobKind, origin, target { companyId, departmentId, agentId, name } | null, trippedAt, reason, clearedAt, clearedReason }`, with no `tripped_by` or `cleared_by` label (the actor-label rule below); a tenant `job_kind` stop is listed read-only.
- **SpendSummary:** `{ asOf, windowStart }`; `tenantRows[]` for the tenant budget and any company budgets, each with `scope, companyId, timezone`, `dailyLimit`, `charged`, `settled`, `estimated`, `remaining` (micros and USD strings), `runningRuns, unknownCostRuns, refusedRuns, settledExhausted, newRunAdmission`; `today { byAgent[], byModel[] }` (tenant only); `platform { globalAdmissionBlocked }`. All arithmetic in SQL.
- **CommunicationStatusSummary (optional):** `channels[] { id, label, mode, active, agent { id, name }, updatedAt }`; `inbound { admittedToday, refusedTodayByReason }`; `conversationsActive24h` (a count); `outbound { byStatus, blockedByReason, indeterminateOpen, acceptedWithoutSend }` (counts only); a fixed note that unrouted deliveries are never stored (SI-53).
- **Page&lt;T&gt;:** `{ items: T[], nextCursor: string | null }`.

**No raw actor labels (PR #6 architecture review, 2026-09-22).** The stored actor columns are free-form: `review_items.reviewer` and `outbound_messages.requested_by` accept any printable ASCII of 1 to 200 characters (`20260917190000_lead_triage_pilot.sql:282`, `20260918150000_whatsapp_transport.sql:258`), and `execution_stops.tripped_by` and `cleared_by` accept `@` (`20260914120000_agent_runtime.sql:244,247`), so a historical row written through the owner CLI can hold an email address, a person's name or any other label. No browser projection returns a raw actor label: the stored reviewer, `requested_by`, `tripped_by`, `cleared_by`, `marked_by`, `configured_by`, `set_by`, `ended_by` and `recorded_by` values and a principal's owner-typed `display_name` are omitted, and 2C adds no replacement identity field (the status, `reviewedAt` and the stop's `origin` are enough). `EventSummary.source` is returned only when it is one of a pinned allowlist of provenance labels that the engine, the gateway and the Company OS gates write (measured at implementation; `operator-cli` and `company-os-ui` among them) and as `other` otherwise, because `events.source` is a caller-supplied label (`20260912200000_company_domain_core.sql:341`). The owner CLI keeps showing the stored labels, and the database columns are unchanged.

**Leaving room for Phase 2D.** Every envelope carries `v`. A later optional `decision` or `shadowSuggestion` section on TaskDetail or ReviewDetail can be added with its own projection, without changing either act's signature (§22).

## 10. Agent state and truthfulness rules

`ops.agent_operational_state(p_tenant_id)` computes state in SQL at read time, from facts, capturing `as_of` once. Two orthogonal axes plus attention, because one enum would hide "working while stopped": a call already in flight when a stop trips is allowed to finish (ADR 0017).

- **Availability** (inactive, then stopped, then available): *inactive* when the agent's, its department's or its company's status is `inactive` (`20260912200000_company_domain_core.sql:193-257`); *stopped* when a stop **naming the tenant** covers `agent_run.execute` for the agent's company, department or agent (deny-wins over the tenant's own stops). A platform stop does not set availability; it is conveyed by `platform.globalAdmissionBlocked` (§9).
- **Activity** (working, stale, held, queued, idle): *working* when an `agent_runs` row has `status = 'running'` and its job is `leased` with `lease_expires_at > as_of` and `attempts = job_attempt` (the negation of the CLI's `RUNNING_WITHOUT_LIVE_LEASE`, `engine/domain/runtimeReadModelRuns.ts:100-108`); *stale* when a running run lacks that live lease (shown as attention, never as working); *held* when a pending run's queued job is covered by `ops.job_covering_stop` (decision B; a platform stop can set this, §9 item 2); *queued* when a pending run's job is queued with no covering stop; *idle* otherwise.
- **Attention:** indeterminate runs that no later run retries, plus stale runs (the CLI's `ATTENTION_WHERE`).

**UI rules:** "working" appears only with at least one evidence id, each linking to its run (no UI-only working state); stopped and working are shown together when both hold; task lifecycle status is never shown as progress (the Tasks screen shows the derived `pipeline`); `needs_edit` renders as "recorded; no follow-up path in this phase"; a state older than two polling intervals renders as "unknown"; no optimistic updates.

## 11. Activity, cursors and pagination

**Cursor format:** `<kind>1:<uuid of the last row returned>` (`ev`, `rn`, `tk`, `rv`, `st`), opaque to clients; `nextCursor` is exactly `<kind>1:<id of the last item>`, so nothing else can hide in it. The server looks the cursor row up **inside the caller's tenant**; a malformed cursor, a wrong kind, a foreign tenant's id, a platform row's id and an erased row all give the same OS400 ("restart from the first page"), so there is no existence oracle.

**Ordering:** events by `(created_at desc, seq desc)`, with `seq` used **only inside the function** as the tie-break that restores insertion order within a transaction; other lists by `(created_at desc, id desc)`; the pending review tab oldest first.

**No global monotonic identifier reaches the browser (SI-26, SI-56):** no output, cursor, offset or total contains `seq`, `job_events.id` or a value derived from a global sequence. ADR 0019 records this reader as the SI-26 "review event" (`docs/SECURITY_INVARIANTS.md:108`).

**Late commits:** a transaction that commits after a page was read lands on an older page; the feed is a view, not a ledger; refresh re-reads the first page; no "newer than" cursor is offered.

**Indexes (forward migration):** `ops.events (tenant_id, created_at desc, seq desc)`; `(tenant_id, created_at desc, id desc)` on `ops.agent_runs`, `ops.tasks` and `ops.review_items`. EXPLAIN checks confirm each is used.

**The inspectable chain.** Lead-triage and outbound events use subject `task` (`20260917190000:560,569,624,715`; `20260918150000:690,700,934,1085,1125,1138,1196,1237`); run lifecycle events use subject `agent_run` (`20260914120000_agent_runtime.sql:817-851`). Insertion order is not step order: admission writes `task.created`, `task.assigned`, `agent_run.requested`, `task.execution_requested`, then `communication.received` and `lead_triage.admitted` in one transaction (`20260918150000_whatsapp_transport.sql:674-702`), so the chain view lays facts out by step and shows each fact's own time. A step with no durable fact is shown as absent, never inferred:
- event received → `communication.received`, `lead_triage.admitted`;
- task created → `task.created`, `task.assigned`;
- run requested → `task.execution_requested`, `agent_run.requested`;
- **job leased → no `ops.events` fact.** An id-free projected step `{ step: job_leased | job_deferred | job_retry | job_reaped, attempt, at }` is read inside the tenant from the run's own job (`ops.job_events`, `20260912120000_ops_execution_core.sql:130-140`, with `deferred` added at `20260917120000_runtime_governance.sql:365-367`), carrying nothing else from the row; `job_deferred` is the stop-held release, which gives the attempt back;
- provider call begun → `agent_run.started` (committed before the call leaves the process; whether the provider was reached is known only from the settlement);
- result settled → `agent_run.succeeded`, `agent_run.failed` or `agent_run.indeterminate` (`'agent_run.' || status`, `20260914120000_agent_runtime.sql:832`); a run refused at request time ends `agent_run.cancelled` (`20260917120000_runtime_governance.sql:2007,2025`);
- review opened → `lead_triage.review_pending`; operator decision → `lead_triage.reviewed`;
- outbound send requested → `communication.outbound_authorized`, then `communication.outbound_attempted` or `communication.outbound_blocked`;
- provider result or status → `communication.outbound_sent`, `communication.outbound_failed` or `communication.outbound_indeterminate` (`'communication.outbound_' || outcome`, `20260918150000_whatsapp_transport.sql:1196`), then `communication.delivery_updated`.

**The payload allowlist is deny-by-default:** `lead_triage.reviewed` → `{ decision }`; `communication.inbound_refused` → `{ channel_id, reason }`; `communication.outbound_*` → `outbound_message_id`, plus `review_item_id` for `outbound_authorized` and `reason` for `outbound_blocked`, never `marked_by` (`20260918150000_whatsapp_transport.sql:1085-1086,1125-1127,1138-1139,1196-1197,1237-1238`); `*.status_changed` → the states only; `communication.channel_configured` → `{ channel_id, mode, active }`; an unknown type → `{}`. A test fails when a migration emits an event type with no allowlist entry.

## 13. Minimisation and browser-handling rules (OD-5, OD-7, OD-10)

1. **Projections, never rows.** Every L2 function builds its output from an explicit column list.
2. **Never returned by any read:** `tasks.title` and `tasks.description`; `agent_runs.result` (including its `response_draft`), prompts and `input_fingerprint`; `inbound_messages.contact_ref`, `external_message_id`, `body_fingerprint`, `crm_contact_ref`; `conversations.contact_ref`; `jobs.last_error`, `lease_owner` and payloads; `job_events` ids and detail; `worker_instances` rows; `correlation_id`, `idempotency_key`, `request_fingerprint`, provider request, response and message ids; the outbound check jsonb; `events.seq`; `communication_channels.provider_target` and `configured_by`; any Auth or CRM email field, `email_at_grant_sha256` and any other email hash; the raw free-form actor labels (`review_items.reviewer`, `outbound_messages.requested_by`, `execution_stops.tripped_by` and `cleared_by`, `spend_limits.set_by` and `ended_by`, `model_prices.recorded_by`, the `marked_by` payload key) and a principal's `display_name` (§9); every platform-scoped row, amount, reason, actor or identifier (platform stops, the global ceiling, price rows, worker instances), other than the pinned platform-derived set (§9); every other tenant's data. These are identity and secret fields, and the rule for them is absolute in 2C: widening it would need an explicit owner decision and an amendment of SI-56, and this phase adds no such projection. Free-text content that reads do return (a review's decision note, a stop's reason and clear reason, on explicit open the advice summary and recommended next action, and the tenant's own owner-typed configuration labels — the tenant, company, department and agent names and a channel label, which are organisational vocabulary, not a person's identity) is content, not identity: a person or the model may have written anything there, an email-like string included, so the design does not claim it is free of email-like text and redacts nothing heuristically. That content is synthetic or test only in 2C, and the real-data gates stay in force before any real data (§5).
3. **The one content exception is the review advice** (`get_review_advice`): the `lead_triage` classification enums, summary and recommended next action, shown nowhere else. **Never the reply draft**, the stored inbound body or any task description, the sender's stored number, a secret, an access token or a raw provider error; the summary and recommended next action are model-written from the message and may echo its words, which is why the read is limited to synthetic or test origins. It requires all of, in this order: the review looked up inside the caller's tenant (OS404 otherwise, before any other branch); a capability with a pinned projection (only `lead_triage` in 2C); an admission row for the task whose source kind is `synthetic`, or `whatsapp` on a channel whose `mode = 'test'`, read at call time (a task with no admission row, any other source kind, or a channel no longer in test mode is withheld, so content stops appearing if production ever opens); a proposal that re-validates against the capability's output contract; an explicit open, never a list; `Cache-Control: no-store`, a memory-only query with `gcTime: 0`, and never logged. This is the SI-52 amendment (§15); the Phase 2B minimisation rule otherwise stays in force.

## 14. Security analysis

1. **Isolation inside the owner-executed projections.** The G functions and their L2 callees execute as the table owner, so a wrong `WHERE` clause could leak across tenants. Mitigations: the graph confines what can be called (§7.3); the resolver-first shape; explicit-tenant L2 functions; reference classification (§7.4); no dynamic SQL; a catalogue-driven two-tenant matrix; sentinel scans; and a differential test: tenant A's outputs are byte-identical, apart from `asOf` and `serverTime`, whether tenant B is idle or busy; a second case drives B's spend to trip `system:spend_ceiling` and adds a platform stop, and asserts that A's outputs change only at the pinned platform-derived paths (§9). Residual: a wrong query the tests miss. An RLS-backed reader role owning the read projections is a recommended hardening; its status before real data is an owner decision.
2. **CRM administration can capture a member's login: a real prerequisite debt (owner decision, final confirmation).** Whoever controls an existing member's auth login can act as that member: `service_role` through the Auth admin API, the JWT signing secret, Auth administrators, and — through the `users` edge function — any CRM administrator, the active CRM owner included, until the S7 prerequisite fixes both the ordering and the authority (an email change followed by password recovery; a CRM-disabled member with an unexpired token can also lift their own ban). What Phase 2C does: explicit membership (nobody but the owner credential can mint a new operator); the principal is the auth user id, so an email change can never retarget a membership to another subject; the Phase 2C eligibility policy (no cross-tenant capture); the live-session and ban checks; `npm run ops -- membership revoke`, not CRM disable, as the Company OS revocation; the `email_at_grant` alarm in `membership list`, which is **detection only, not an authorization boundary**. **Owner decision:** this risk is accepted only for local, synthetic and test Phase 2C. **Real data and any hosted operator surface are blocked** until the `users` edge function's `patchUser` and `createSale` authority and ordering issues are fixed and tested, so that no CRM administrator, the active CRM owner included, changing profile or user information can retarget or acquire another person's Company OS principal (§19 S7). After S7, the remaining capture paths are `service_role`, the JWT signing secret and Auth administration, the platform's own trust root.
3. **Claim forgery.** `request.jwt.claims` can be set by any session that can `SET ROLE authenticated` (`postgres`, `authenticator`, the sealed `merge_contacts` pool; the R-16 shape, `docs/PHASE_2B_REPORT.md:390`). Mitigations: only `authenticated` holds EXECUTE on L3; every member of `authenticated` and of `ops_operator_api` is pinned (§15); the pool fails closed on the legacy claim; the live-session check requires a real `(auth user id, session id)` pair. Residual: the `postgres` credential already dominates the database; the `authenticator` credential reaches member data only with a live user id and session id pair. 2C neither resolves nor depends on the PUBLIC helper debt.
4. **The role-ownership mechanics.** An allowlisted migration temporarily makes the proven migration identity a member of `ops_operator_api` and grants the role CREATE on `company_os_api`. Mitigations: both are revoked in the same migration; each allowlisted migration is pinned by its exact file name and carries the whole lifecycle itself, with no standing exception for later work (§7.6 A); the end state (§7.6 E) is asserted by the migration and pinned by the suite; the pinned OD-8a exception refuses any other membership, ownership change, CREATE or role switch (§7.6). These are PostgreSQL 15 facts (§4.3 item 8).
5. **Token theft (owner decision, final confirmation).** A stolen valid user session is a real threat, and the Company OS membership table does not solve it: **membership limits what a valid principal may access; it does not prove the token was not stolen.** The SPA has no CSP, keeps the Supabase session in `localStorage` and publishes sourcemaps. A stolen member token can read the tenant's projections (test data), open the advice (its classification enums, summary and recommended next action), decide pending reviews (final) and trip stops (denial of service); it cannot send, clear a stop, configure a channel, touch money, reach platform scope, read a reply draft or read another tenant. **Owner decision:** ordinary Supabase authenticated-session risk is accepted for synthetic and test Phase 2C development; this approves no real patient traffic. Before real patient or production operator use the existing gates remain: session hardening, an MFA decision and implementation, a CSP, a hosted exposure review, and auth and user-management hardening. A CLI send transmits the reply draft of an accepted review, and its checks do not look at who accepted that review; the accepting principal is visible in `triage list` and `show` (showing the reviewer and source in `messaging -- send` itself is recommended); the unread-draft residual is item 11.
6. **Hosted configuration drift.** Exposing `ops`, or putting `company_os_api` on the search path, from a dashboard or `supabase config push` is invisible to repository checks. Mitigation: local and test only; a separate hosted-readiness step with a blocking verification (OD-12); the runbook forbids Supabase's default custom-schema grants.
7. **The PUBLIC default EXECUTE.** Mitigations: explicit revokes; USAGE only where the graph needs it; the end-state assertion; ACL pins; K4 and K5.
8. **Errors leak through PostgREST.** Mitigations: G functions raise one fixed message per operation and SQLSTATE and map anything else to OS500 with no detail; reads validate every input; tests compare every refusal body, SQLSTATE, message, detail and hint with the refusal for a fresh random uuid.
9. **Kill-switch lock effects (owner decision, final confirmation).** `trip_execution_stop` takes the platform-wide exclusive lock that also serialises run admission, and the owner accepts that serialised behaviour. A member tripping in a loop could delay other tenants' leases and starts, and a trip's lock wait is a timing signal about other tenants' concurrent lease and start activity. **Required behaviour:** no separate pre-check; the authoritative service; deny-wins, serialisation with run admission, audit and origin all preserved; a **bounded** request (the gate's pinned `lock_timeout`, inside PostgREST's statement timeout; NOT MEASURED until S0.4, M4 and M11, and if the bound cannot be shown the phase stops for owner review) that never hangs; on contention (the gate's `lock_timeout` expiring) one generic, retryable refusal (OS429), and on a statement timeout PostgREST's own generic error, neither revealing any other tenant, job, execution state or timing beyond the bound; the UI never shows a stop as created before the database commits it; driver-backed tests exercise contention (§16). Spike S0.4 fixes the bound and measures the effect on another tenant.
10. **Governance drifts into React.** Mitigations: the UI evaluates nothing; `allowedActions` are hints; the `CompanyOsApi` port has no clear, send, configure, retry or production method; the act functions do not exist before the prerequisite.
11. **Acceptance mistaken for sending.** Mitigations: zero outbound rows and jobs after accept (SQL and driver); no send control; the confirmation text; SI-45 restated; the explicit semantics of §7.5 (a browser decision decides the structured review, never the hidden draft, authorises no send, and is never presented as a message approved for sending), tested in §16. The owner accepted the draft's exclusion from the browser at the pre-push review. **Residual (a consequence of the SI-52 amendment, recorded for the owner, not decided):** a member who accepts in the browser never sees the reply draft, yet that acceptance is what a later send requires (ADR 0018 §4); `npm run messaging -- send` transmits the draft without displaying it, and the only view of it is `npm run ops -- triage show`, which the send does not require, so reviewing the draft before a send is an operator procedure, not an enforced check.
12. **The data class is owner-asserted.** `synthetic` and `test` are labels, not proof: a Meta test number accepts a message from any WhatsApp user, the synthetic ingress accepts any text, and a channel's `mode` is owner configuration. The origin gate withholds the advice for production channels but cannot prove content is not real. This is Phase 2B's residual (connect only test numbers carrying test data), restated in ADR 0019.
13. **Operator code in the public bundle and PWA precache** (`vite.config.ts:34-41`): code only, no data or secret, and the repository is public. `vite.config.ts` is not changed in 2C.

## 15. Invariants and guards

**Proposed new security invariants.** The numbers are **provisional**: at `d1819f25` the registry uses SI-01 to SI-53 (SI-07 retired) and SI-54 upward is unused (`supabase/tests/securityInvariants.test.ts`, `docs/SECURITY_INVARIANTS.md`). This planning task adds none to the registry.

- **SI-54 — The operator API surface and its capability graph.** `company_os_api` holds exactly the catalogued functions and no relation, sequence or type. Each L3 function is SECURITY DEFINER with `search_path = ''`, owned by `ops_operator_api`, executable only by `authenticated` (and, implicitly, by its owner), and its body is exactly one call to its G function. `ops_operator_api` is NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOBYPASSRLS and NOINHERIT, has no members at rest and is in no login role's membership closure, holds USAGE on `ops` and EXECUTE on exactly the G set (and, outside `ops`, `pg_catalog` and `information_schema`, in a schema where it holds USAGE, only a pinned measured list), and holds no table, column or sequence privilege outside the catalogue reads PUBLIC gives every role and no CREATE on any schema or on the database. `ops` stays off the Data API.
- **SI-55 — Identity and membership derivation.** A browser caller's tenant and actor come only from `ops.operator_scope()`: verified PostgREST claims, a live session, an existing unbanned auth user, an enabled human principal keyed to that auth user id, and exactly one active membership of a tenant that satisfies the Phase 2C eligibility policy. An email never selects, identifies or authorises a principal or a membership. No L3 or G function takes a tenant, company, actor, reviewer, source or causation context parameter, and every uuid argument it does take is a pinned selector resolved inside the membership-derived tenant. Memberships are written only through the owner credential, only for human principals, and are never re-pointed to another auth user or tenant; no CRM role or administrator state derives Company OS authority.
- **SI-56 — Tenant isolation and minimised projections** (narrowly extended at the PR #6 architecture review, 2026-09-22: identity fields and raw actor labels). No browser-facing output carries another tenant's data, a stored message or task body, a stored phone number, a reply draft, a raw job error, a provider secret or internal id, a global sequence value, a platform-wide identifier, an Auth or CRM email, an email hash, or a raw free-form actor or reviewer label (a stored reviewer, requested_by, tripped_by, cleared_by, marked_by, configured_by, set_by, ended_by or recorded_by value, or a principal's display name); an event's source is returned only when it is in a pinned provenance allowlist, and as the fixed value other otherwise. Free-text content a projection returns (a decision note, a stop reason and clear reason, the advice summary and recommended next action, and the tenant's own owner-typed configuration labels: tenant, company, department and agent names and a channel label) is content, not identity, and is not claimed free of email-like text. Platform state is limited to the pinned platform-derived set. The `lead_triage` classification enums, summary and recommended next action appear only through the capability-pinned advice projection, on explicit open, for synthetic or test origins; the summary is model-written and may echo the message it describes (SI-52).
- **SI-57 — Truthful working state.** An agent is reported working only while a running AgentRun holds a live job lease, and the report carries that run's id.
- **SI-58 — Browser authority.** The browser can cause exactly two mutations, and only once their functions exist after the user-management prerequisite: a review decision through `ops.record_review_decision` (which decides the structured review only, approves no reply draft, authorises no send, and writes no outbound row and no job), and a trip at tenant, company, department or agent scope through `ops.trip_execution_stop` under its lock, with a bounded wait whose contention answer is generic, retryable and creates nothing. It cannot clear a stop, trip a global, system or `job_kind` stop, send, resend, retry or mark a send, configure or activate a channel, or change money, organisational-unit, CRM or governance state.
- **SI-59 — Browser handling.** No Company OS data reaches durable browser storage, and no provider, database or transport secret reaches a bundle.

## 22. Phase 2D and 2E direction (recorded, not implemented)

**Phase 2D — Decision engine.** A provider-neutral **DecisionPort** with three planned implementations: **JevDecisionProvider**, **RulesDecisionProvider** and **FakeDecisionProvider**. Its core output is a **DecisionVector**, whose likely fields include `route`, `task_type`, `complexity`, a risk signal or classification metadata, `urgency`, `ambiguity`, `required_capabilities`, and a confidence or probability distribution where the provider supports one.

The following flow is illustrative; the Phase 2D brief proposes the data flow for the owner's explicit decision:

```
Event
  ↓
DecisionPort
  ↓
Jev / Rules / Fake
  ↓
DecisionVector
  ↓
Company Engine deterministic policy
  ↓
Model Router
  ↓
Model
  ↓
future evaluation / escalation
```

- **Jev is not authoritative** for permission, the tenant boundary, budgets, the kill switch, lawful basis, consent, risk-policy enforcement or irreversible actions. AI interprets uncertainty; the Company Engine applies policy; models execute bounded work; evaluation may escalate.
- **Jev enters in shadow mode first.** Its decisions are measured against actual routing outcomes, human decisions, model outcomes, latency, cost, calibration and escalation quality.
- **No real patient data** until every prerequisite for real patient traffic is met: Q8 decided, the Phase 2B owner decisions made, the Accepted ADR that ADR 0018 amendment 1 requires, the live Meta test probe, and the decision on the PUBLIC CRM helper grants. Jev's Q8 impact is assessed in the Phase 2D brief and presented for the owner's explicit decision; Q8 stays an owner decision, and OPEN.
- **Nothing of Jev is added in 2C:** no SDK, API call, environment variable, schema or migration. "Jev" appears only in the planning records (this brief, ADR 0019, `docs/DECISIONS.md`, `docs/ROADMAP.md`, `CLAUDE.md`); its definition and data flows are proposed in the Phase 2D brief for the owner's decision.

**Phase 2E — Observability and intelligence.** Expected concerns: decision quality; Jev calibration; model performance; model and provider latency; cost; escalation metrics; failure and indeterminate rates; agent, run and workflow visibility; provider health. Not implemented.

**How 2C leaves a clean place for Decision data without implementing it:** the identity gate accepts only `human` principals, and memberships are human-only by constraint, so no engine component or decision provider can act through the human surface (agents keep the ADR 0011 Tool Gateway path); neither act has a parameter through which a DecisionVector could enter; envelopes are versioned (`v`), so an optional `decision` or `shadowSuggestion` section can be added later with its own projection; 2C adds no "Decisions" screen and no metrics store.
